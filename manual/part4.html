1. 왜 측정이 따로 한 부(部)나 되는가

강화학습 프로젝트를 하다 보면 이상한 일이 생겨. 손실(loss)은 매일 내려가는데 AI가 정말 강해졌는지는 아무도 모르는 거야. 손실은 "신경망이 자기가 만든 데이터를 얼마나 잘 따라 하는가"를 재는 숫자지, "오목을 얼마나 잘 두는가"를 재는 숫자가 아니거든. 그래서 이 프로젝트는 처음부터 끝까지 "실력을 어떻게 잴 것인가"라는 질문과 계속 씨름했어.

이 부에서 다루는 측정 도구는 다섯 가지야. 각각 재는 대상과 쓰임새가 다르다는 점을 먼저 머리에 넣어 두자.

2. 기초 통계: 승률, 점수, Elo, 표본 크기

2.1 점수 s

오목에는 무승부가 있어. 그래서 단순 "승률"보다 점수(score)를 써. 이 프로젝트의 모든 측정 코드는 같은 정의를 써.

s = (wins + 0.5 * draws) / games

이긴 판은 1점, 비긴 판은 0.5점, 진 판은 0점. 예를 들어 20판에서 8승 8무 4패면 s = (8 + 4) / 20 = 0.60이야. 실제로 epoch 625가 게이트를 통과했을 때 성적이 정확히 이거였어(README.txt: "gate 20g: W8 D8 L4 = 60%, promoted").

2.2 Elo 차이

Elo는 체스에서 온 실력 척도야. 핵심 가정은 하나뿐이야: 두 선수의 Elo 차이가 D면, 강한 쪽의 기대 점수는

s = 1 / (1 + 10^(-D/400))

이 식을 D에 대해 거꾸로 풀면 rapfi_ladder.py에 있는 식이 나와.

D = 400 * log10( s / (1 - s) )

직접 풀어 보자. s(1 + 10^(-D/400)) = 1 → 10^(-D/400) = (1-s)/s → -D/400 = log10((1-s)/s) → D = 400·log10(s/(1-s)). 끝이야.

2.3 0%와 100%의 문제: 클램프

s = 1이면 s/(1−s)가 무한대가 돼서 Elo가 무한이 나와. 10판 다 이겼다고 "무한히 강하다"고 할 수는 없지. 그래서 코드는 값을 잘라(clamp) 둬.

def elo(score, n):
    lo, hi = 1.0 / (2 * n), 1.0 - 1.0 / (2 * n)
    s = min(max(score, lo), hi)
    return 400.0 * math.log10(s / (1.0 - s))

20판이면 s는 [0.025, 0.975] 범위로 잘려. "반 판 정도는 운이 달랐을 수 있다"는 보수적 가정이야. 뒤에 나올 직선 맞춤(fit) 코드는 이와 별개로 [0.03, 0.97]로 자르는데, 두 곳의 클램프 값이 다르다는 점은 기억해 둬.

2.4 표본 크기: 20판은 얼마나 믿을 만한가

참 실력이 정확히 p = 0.5인 상대와 n판을 두면, 관측 점수의 표준편차는 대략 √(p(1−p)/n)이야(무승부가 있으면 이보다 약간 작아져).

주의: 위 표는 "매 판이 독립적인 동전 던지기"라는 가정에서 나온 거야. 그런데 이 프로젝트의 사다리는 운이 전혀 섞이지 않는 결정적 측정이라는 게 나중에 밝혀졌어(11절). 그럼 "노이즈"는 어디서 오는 걸까? 답은 "같은 모델을 다시 재는 데서"가 아니라 "모델이 조금 바뀔 때 20개 시작 국면 중 몇 개의 결과가 뒤집히는 데서" 와. 표준편차 표는 그 민감도를 가늠하는 용도로 읽어야 해.

3. 게이트 (승격 시험)

3.1 왜 게이트가 필요한가

신경망은 경사하강법으로 매 에폭 조금씩 바뀌어. 그런데 바뀐다고 매번 좋아지는 건 아니야. 이 프로젝트는 실제로 비이행적(non-transitive) 실력을 측정했어: 어떤 체크포인트가 500에폭 전 모델은 이기는데 100에폭 전 모델에게는 지는 현상. 코드 주석을 그대로 보자.

# A self-play policy trained by continuous gradient descent isn't guaranteed
# to improve monotonically -- this project directly measured non-transitive
# strength between checkpoints (beats one from 500 epochs ago, loses to one
# from 100 epochs ago). AlphaGo Zero's fix was to never let raw, unvalidated
# weights become the new baseline: a candidate must actually beat the current
# best in fair (no-noise, full-search) play before it's promoted.

그래서 AlphaGo Zero처럼 "최고 모델(best)"을 따로 보관하고, 학습 중인 모델이 그 최고 모델을 공정한 대국에서 이길 때만 교체해. 이게 게이트야.

  1. 대부분 "유지"야. 13번 중 2번만 승격. 승격은 정확히 기준선(0.55)에 걸쳐서 일어났어. 20판짜리 시험에서 "기준선에 딱 걸친 통과"는 운의 영향을 크게 받아.
  2. 무승부 비율이 높아. 비슷한 실력의 두 모델이 노이즈 없이 두면 비기는 판이 많아. 무승부가 많을수록 승격은 어려워져(무승부는 0.5점이라 평균을 0.5 쪽으로 끌어당기니까).
게이트 정체(stagnation)의 역사. 코드 주석에는 "252 straight 0%-loss gate checks" 끝의 epoch 273 첫 승격, Gen10 재시작 이후 "gate-check having stayed stuck at ~0% for 564+ epochs" 같은 기록이 남아 있어. 그리고 2026-09-30에는 "gate stuck 15 checks (650-720) while losses kept falling"이라는 이유로 학습률 대역을 절반으로 낮췄어(1e-4..5e-5 → 5e-5..1e-5). 손실은 내려가는데 게이트는 막혀 있다는 게 이 프로젝트의 단골 증상이었고, 이것이 외부 자(Rapfi)가 필요했던 이유 중 하나야. 게이트는 "어제의 나"와만 비교하니까, 둘 다 같은 방향으로 틀려 있으면 아무것도 못 잡아.

3.4 게이트와 연동된 장치들

게이트 결과는 학습의 다른 부분도 움직여. 자세한 건 학습 루프를 다룬 부에 있지만, 측정 관점에서 알아둘 것만 적을게.

  • 탐색량 램프: 승격할 때마다 자가대국 시뮬레이션 수를 SIM_RAMP_STEP=100씩 올려(시작 150, 상한 1100). 승격 없이 STAGNATION_RAMP_LIMIT=5번 연속 유지되면 그래도 한 단계 올려.
  • LR 쿨다운: 승격 직후 LR_COOLDOWN_EPOCHS=25 동안 학습률 스케줄러를 얼려. 승격 직후 모델이 불안정한 구간에 학습률 재시작이 겹친 사고(epoch 273 승격 후 300에서 재시작)가 실제로 있었기 때문이야.

4. vs-Det: 결정론적 미니맥스 상대 평가

이 프로젝트의 원래 연구 목표는 3x3 시절부터 "결정론적 알고리즘(미니맥스)을 이긴다"였어. 그래서 가장 오래된 측정은 evaluate_vs_deterministic이야. docstring이 목적을 그대로 말해 줘.

    Plays num_games against determinisic_play (minimax/alpha-beta), alternating
    who moves first, and returns (win_rate, draw_rate, loss_rate) from the
    trained model's perspective. This is the direct metric for the research
    goal ("beat the deterministic algorithm").

11x11에서 상대는 determinisic_play.py의 MAX_DEPTH = 2, 즉 2수 앞을 보는 알파-베타 탐색이야. 메모리 노트에도 "depth-2 minimax is just the baseline"이라고 적혀 있어: 진짜 목표는 평균적인 사람을 이기는 거고, 미니맥스는 바닥선일 뿐이야.

4.1 결정론적 상대의 함정: 같은 판의 반복

미니맥스는 랜덤이 없어. 우리 모델도 평가 때는 노이즈 없이 둬. 그러면 같은 시작 국면에서는 매번 똑같은 판이 나와. 이게 두 가지 버그를 낳았어. 코드 주석에 둘 다 남아 있어.

# evaluate_vs_deterministic (see its docstring): with only len(_OPENING_SQUARES)
# distinct openings, requesting a game count not coprime with that count made
# many "games" exact repeats of an earlier one under a different index label.
...
# Gen3 eval-diversification (2026-09-09): row-major order meant every vs-Det

  1. 중복 판 버그: 시작 국면 종류가 적은데 판수를 많이 요청하면, "10판"이 실제로는 같은 판 몇 개의 복사본이었어. 그러면 10판 측정이 사실상 3~4판 측정이 돼.
  2. 왼쪽 위 편향 버그: 모든 칸을 행 순서(row-major)로 나열한 뒤 앞에서부터 잘라 썼기 때문에, 평가가 언제나 판의 왼쪽 위 모서리 근처 시작 국면만 봤어. 시드 1109로 한 번 섞어서 해결했어. 시드를 고정했으니 "같은 인덱스 → 같은 칸"이라 재현성은 유지돼.
이 두 버그의 공통 교훈: 결정적인 평가에서 "판수"는 "서로 다른 시작 국면의 수"와 같다. 시작 국면이 겹치면 판수를 늘려도 정보가 늘지 않아. 이 교훈은 뒤에서 Rapfi 사다리에서 그대로 다시 나타나.

4.2 후반부의 vs-Det

후반(v13 로그)에서는 정식 평가가 "Eval vs Deterministic (5 games, 600 sims/move, openings seed=720): Win 100%" 같은 형태로 찍혀. 학습 설정(_restart_train.py)도 eval_games=5, eval_simulations=600이야. 이 단계에서 깊이 2 미니맥스는 이미 변별력이 없는 상대가 됐고, 그래서 외부의 더 강한 자가 필요했어. 그게 Rapfi야.

참고로 학습 데이터용 vs-Det 대국(_sample_vs_det_max_depth(epoch)로 상대 깊이를 에폭에 따라 뽑음)은 평가와 분리돼 있어. 주석: "evaluate_vs_deterministic/run_gating_check hold as an untouched promotion metric". 평가용 상대는 건드리지 않는다는 원칙이야. 그리고 현재 설정은 num_vs_deterministic_games=0, refresh_vsdet_games=0이라 학습 쪽 vs-Det 대국은 꺼져 있어.

5. Rapfi라는 자(尺)

5.1 Rapfi는 무엇인가

Rapfi는 오목 AI 대회 Gomocup의 2024년 우승 엔진이야(rapfi_match.py 첫 줄: "Our model vs Rapfi (Gomocup 2024 champion engine), 11x11 freestyle"). 실행 파일은 engines\rapfi\pbrain-rapfi-windows-avx2.exe야. 이 엔진의 구조를 대화 기록에서 정리했던 내용을 요약하면:

  • 알파-베타 계열 탐색 + 강력한 위협 해법기(VCF 등).
  • 평가 함수는 원래 신경망(Mixnet, 그리고 15x15에서는 NNUE 방식의 작은 신경망)을 쓰는데, KataGomo가 만든 대량의 국면으로 증류 학습한 가중치야.
  • 그런데 11x11용 가중치가 없어서 신경망이 꺼진다. 그래서 우리가 상대한 건 사람이 설계한 전통적 패턴 평가 버전의 Rapfi야.
보고서 표기 규칙. 대화 기록(2026-09-28경)에서 정한 대로, 결과를 쓸 때는 "Rapfi (11×11, 신경망 평가 비활성)"이라고 명시해야 해. "Gomocup 챔피언과 대등"이라고만 쓰면 과장이야. 우리가 이긴 상대는 Rapfi의 최상위 형태가 아니야. 이 점이 15x15로 넘어가고 싶은 이유 중 하나이기도 해: 15x15에서는 Rapfi 최강 버전과 비교할 수 있으니까.

(신경망 비활성 여부를 Rapfi 출력에서 직접 확인한 원문 로그는 이번에 찾아보지 않았어. 위 내용은 대화 기록의 설명에 근거해.)

5.2 "자"로서 Rapfi의 장점

  • 외부 기준: 우리 모델과 같은 방향으로 틀릴 이유가 없어. 게이트의 "자기 자신과 비교" 문제를 피해.
  • 세기 조절 가능: 탐색 노드 수를 제한하면 아주 약한 Rapfi부터 매우 강한 Rapfi까지 연속적인 사다리를 만들 수 있어.
  • 측정 전용: rapfi_match.py 머리 주석: "MEASUREMENT ONLY (2026-09-28) -- nothing here feeds training." Rapfi의 수가 학습 데이터로 들어가지 않아. 자가 지도학습(AlphaZero 원칙)을 지키면서 바깥에서 재기만 해.

    def move(self, moves, me):
        """moves: list of (player, r, c) played so far; me: Rapfi's color."""
        self.send("BOARD")
        for pl, r, c in moves:
            self.send(f"{c},{r},{1 if pl == me else 2}")  # Gomocup: x=column, y=row
        self.send("DONE")

세 가지 디테일이 중요해.

  1. 좌표 순서: 우리 코드는 (행 r, 열 c)인데 Gomocup은 (x=열, y=행)이야. 그래서 보낼 때 f"{c},{r},...", 받을 때 return int(y), int(x)로 뒤집어. 이걸 틀리면 판이 대각선으로 뒤집힌 채 두게 돼. 무서운 건 그래도 "대국은 진행된다"는 점이야. 에러 없이 이상한 결과만 나와.
  2. who 값: 1 = 엔진 자신의 돌, 2 = 상대 돌. 색(X/O)이 아니라 "누구 것인가"로 보내.
  3. 무상태(stateless): 매 수마다 BOARD로 판 전체를 다시 보내. 머리 주석: "is sent the full position with BOARD before each of its moves, so it is stateless between moves." 이렇게 하면 엔진 내부 상태가 꼬일 일이 없어. 대신 엔진의 이전 탐색 트리를 재사용하는지는 엔진 구현에 달렸어(확인 안 함).

rapfi_match_log.jsonl의 opening 분포를 세어 보면 (5,5)와 (4,5)가 각 374~375번, 나머지는 170~204번이야. 20판짜리 측정에서 8개 시작점을 순환하면 앞쪽 4개가 3번, 뒤쪽 4개가 2번씩 쓰이니까(20 = 8+8+4), 앞쪽 시작점이 더 많이 나오는 게 자연스러워. (5,5)와 (4,5)가 특히 많은 건 초기의 6판짜리 실험들이 앞에서부터 썼기 때문으로 보여.

"20판 = 20개의 서로 다른 시작"이 아니다. 8개 시작점 × 색 2가지 = 최대 16가지 조합이야. 20판이면 조합 일부가 반복돼. 그런데 반복된 조합이라도 Rapfi의 노드 제한 탐색과 우리 탐색이 둘 다 결정적이면 완전히 같은 판이 될 수 있어. 판 순서상 n번째 판과 n+16번째 판은 시작점과 색이 같아(8과 2의 최소공배수가 8이라 실제로는 8판 주기로 시작점이 돌아오고, 색은 짝홀로 번갈아서 16판 주기). 이 점이 11절의 결정성 발견과 연결돼. 실제로 20판이 몇 개의 "진짜 서로 다른 판"인지는 이번에 판 수순을 비교해 확인하지 않았어.

8. 대등 국면 사다리 (rapfi_ladder.py)

8.1 아이디어

Rapfi의 노드 수를 여러 단계로 바꿔 가며 붙어 보면, 노드가 적을 땐 우리가 이기고 노드가 많을 땐 우리가 져. 그 사이 어딘가에 우리가 정확히 50%를 내는 노드 수가 있어. 이것을 "대등 국면 수(equal-strength nodes)"라고 불러. 이 숫자가 클수록 모델이 강하다는 뜻이야. 하나의 숫자로 실력을 표현할 수 있어서 시간에 따른 추세를 그리기 좋아.

9. 함정 1: 단일 교차점 규칙의 착시 (ep555 "1,250"의 진실)

9.1 원래 규칙

처음 사다리 코드는 이렇게 대등점을 구했어. 지금도 참고용으로 남아 있어.

    # node budget where our score would be 50% (log-linear interpolation)
    eq = None
    for a, b in zip(results, results[1:]):
        if a["score"] >= 0.5 >= b["score"] and a["score"] != b["score"]:
            t = (a["score"] - 0.5) / (a["score"] - b["score"])
            eq = 10 ** (math.log10(a["nodes"]) + t * (math.log10(b["nodes"]) - math.log10(a["nodes"])))

말로 하면: 이웃한 두 단계 a, b 사이에서 점수가 50%를 위에서 아래로 가로지르면, 그 둘을 로그 눈금 위의 직선으로 이어서 50%가 되는 지점을 찾아. 루프가 끝까지 돌기 때문에 교차가 여러 번이면 마지막 교차점이 채택돼.

9.2 ep555에서 일어난 일

9/28 19:54 사다리(대화 기록상 epoch 555 무렵 best)의 결과:

Rapfi 노드승패무점수
10012620.65
3009830.525
10009740.55
300051320.30

300에서 0.525, 1000에서 0.55. 1000 단계가 300 단계보다 오히려 점수가 높아. 이건 실력의 진짜 모양이 아니라 20판의 흔들림이야. 그런데 옛 규칙은 "1000(0.55)과 3000(0.30) 사이에서 50%를 가로지른다"만 봐.

t  = (0.55 - 0.5) / (0.55 - 0.30) = 0.2
eq = 10^( log10(1000) + 0.2 × (log10(3000) - log10(1000)) )
   = 10^( 3 + 0.2 × 0.4771 ) = 10^3.0954 ≈ 1,246

로그에 찍힌 값도 정확히 "equal_nodes": 1245.7309396155179야. 대화에서 이걸 "대등 국면 약 1,250, 기준 1,000 돌파"라고 보고했어.

9.3 무엇이 문제였나

  • 네 단계 중 두 단계만 씀: 100과 300의 정보(0.65, 0.525)는 완전히 버려져.
  • 한 단계의 운에 전부를 걸어: 1000 단계의 20판 중 한 판만 졌어도(0.55 → 0.50 이하) 교차점이 크게 이동해.
  • 교차가 여러 번이면 임의적: 점수가 단조감소하지 않으면 "마지막 교차"가 뽑히는데, 이건 아무 근거 없는 선택이야.

실제로 옛 규칙의 값은 측정마다 100 ~ 1,246 사이를 널뛰었어. 9/28 15:45 측정에서는 100 단계가 정확히 0.5라 대등점이 100.0으로 찍혔어. 코드 주석: "The single-crossing rule above swung 100..1250 on 20-game noise; kept for reference."

사과와 정정의 기록. 9/29 01:28 대화에서 새 방식으로 다시 계산하자 epoch 555는 약 575, epoch 580(옛 규칙 1,000)은 약 382로 바뀌었어. "이미 한 번 1,000을 넘었다"는 전날 밤의 판단은 틀렸다고 공식 정정했어. 그리고 선택지 A(새 방식 + 기준 1,000 유지)와 B(새 방식 + 기준 조정) 중 A를 사용자가 골랐어("A로 하자", 01:29). 기준을 계산법에 맞춰 낮추지 않고, 더 엄격한 쪽을 택한 거야.

10. 새 규칙: 판수 가중 최소제곱 직선

10.1 직관

점(단계) 몇 개 가운데 둘만 고르지 말고, 모든 점을 가장 잘 지나는 직선 하나를 긋자. x축은 log10(노드 수), y축은 그 단계의 Elo 차이야. 그 직선이 Elo = 0(=점수 50%)을 지나는 x가 대등점이야.

왜 x를 로그로 하나? 탐색량을 두 배 할 때마다 실력이 대략 일정량씩 늘어난다는 경험칙 때문이야. 그래서 "노드 수의 로그"와 "Elo"가 대략 직선 관계가 돼. 왜 y를 점수 대신 Elo로 하나? 점수는 0과 1에 갇혀 있어서 끝으로 갈수록 휘어지는데, Elo로 펴면 직선에 가까워지기 때문이야.

10.2 최소제곱이란

점 (xi, yi)들과 직선 y = a + b·x가 있을 때, 각 점의 세로 오차 yi − (a + b·xi)를 제곱해서 더한 값을 가장 작게 하는 a, b를 고르는 게 최소제곱이야. 가중 최소제곱은 각 제곱 오차에 가중치 wi를 곱해서 더해. 여기서 가중치는 그 단계의 판수야. 판을 많이 둔 단계일수록 더 믿을 만하니까.

미분해서 0으로 두면 해가 이렇게 나와 (가중 평균 mx, my를 쓰면 깔끔해):

m_x = Σ w·x / Σ w          m_y = Σ w·y / Σ w
S_xx = Σ w·(x - m_x)²      S_xy = Σ w·(x - m_x)·(y - m_y)
기울기 b = S_xy / S_xx
직선은 (m_x, m_y)를 지남:  y = m_y + b·(x - m_x)
y = 0 이 되는 x*:  x* = m_x - m_y / b
대등 노드 = 10^(x*)

10.3 실제 코드

    crossing = eq
    # 2026-09-29 (user decision): the official equal-strength point is a games-weighted
    # least-squares line of Elo vs log10(nodes) over ALL levels, solved for Elo = 0.
    # The single-crossing rule above swung 100..1250 on 20-game noise; kept for reference.
    xs = [math.log10(r["nodes"]) for r in results]
    ws = [r["games"] for r in results]
    ys = [400 * math.log10(min(max(r["score"], 0.03), 0.97) / (1 - min(max(r["score"], 0.03), 0.97))) for r in results]
    sw = sum(ws)
    mx = sum(w * x for w, x in zip(ws, xs)) / sw
    my = sum(w * y for w, y in zip(ws, ys)) / sw
    sxx = sum(w * (x - mx) ** 2 for w, x in zip(ws, xs))
    sxy = sum(w * (x - mx) * (y - my) for w, x, y in zip(ws, xs, ys))
    slope = sxy / sxx if sxx > 0 else 0.0
    eq = 10 ** (mx - my / slope) if slope < 0 else ("above max level" if my > 0 else "below min level")

위 수식과 한 줄 한 줄 대응돼. 마지막 줄의 조건 slope < 0이 중요해: 노드가 많을수록 우리가 불리해져야 정상이니 기울기는 음수여야 해. 만약 양수나 0이면(데이터가 이상하면) 대등점을 계산하지 않고 "above/below" 문자열을 남겨. 로그에는 equal_nodes(새 방식, 공식), equal_nodes_crossing(옛 방식, 참고), fit_slope(기울기, 노드 10배당 Elo)가 함께 찍혀. 9/29 12:35 로그부터 세 필드가 모두 있어.

10.6 이 방법의 한계 (내가 판단하기에)

  • "Elo가 log(노드)에 선형"이라는 가정은 근사야. 실제로는 곡선일 수 있어.
  • 가중치가 모두 20이라 사실상 일반 최소제곱과 같아. 단계별로 점수의 분산이 다르다는 점(0.5 근처가 가장 큼)은 반영 안 해.
  • 오차 막대(신뢰구간)를 계산하지 않아. 그래서 "1,150 > 1,000"이 통계적으로 의미 있는 차이인지는 이 숫자만으로는 말할 수 없어.

11.2 왜 결정적인가

  1. 시작 국면이 고정: 8개 시작점을 정해진 순서로 순환, 색도 정해진 순서로 번갈아.
  2. 우리 AI에 랜덤이 없음: 디리클레 노이즈 없음, 온도 없이 방문 수 최대 수 선택. 같은 신경망 + 같은 국면 → 같은 탐색 → 같은 수.
  3. Rapfi도 노드 제한이면 결정적: 시간이 아니라 노드 수로 끊으니 같은 국면에서 같은 수.

세 가지가 모두 결정적이면 대국 전체가 결정적이야. 수학적으로 말하면 사다리 결과는 모델 가중치의 순수 함수야.

단, GPU 연산의 비결정성. 이론상 GPU의 부동소수점 연산 순서(배치 크기, 병렬 합산 순서)에 따라 신경망 출력이 소수점 아래 끝자리에서 미세하게 달라질 수 있어. 그게 방문 수 동점을 깨는 방향으로 작용하면 수가 바뀔 수도 있어. 그런데 실측 결과 같은 모델 80판이 완전히 동일했으니, 적어도 이 설정에서는 그런 일이 관측되지 않았어. 반대로 웹 서버에서는 "여러 판이 동시에 탐색하고 트리를 재사용해서 매번 완전히 똑같지 않았던 것으로 보여"라는 관찰이 대화 기록에 있어. 결정성은 설정에 따라 깨질 수 있다는 걸 기억해 둬.

11.3 결정성이 뜻하는 것

  • 같은 모델을 다시 재는 건 의미가 없다. 이후 서버/스크립트는 "가중치가 같으면 한 번만 재도록" 바뀌었어(대화 기록, 9/29경).
  • "측정 노이즈"의 정체가 바뀐다. 555, 580, 600 사이에서 숫자가 크게 흔들린 건 주사위 운이 아니라, 모델이 조금만 바뀌어도 20개 판 중 몇 개의 결과가 뒤집히기 때문이야. 같은 20판으로 모델을 비교하는 건 "고정된 20문제 시험"과 같아. 시험 문제가 적으면 공부를 조금 다르게 했을 때 점수가 크게 출렁여.
  • 그래도 2절의 표준편차 감각은 유효하다. "20개 시작 국면이라는 표본"이 "모든 가능한 국면"을 대표하는지에 대한 불확실성은 여전히 남으니까. 다만 그 불확실성은 같은 모델을 반복 측정해서는 줄일 수 없고, 시작 국면 수를 늘려야만 줄어.
4절과의 연결. vs-Det에서 "결정적 평가의 판수 = 서로 다른 시작 국면 수"라는 교훈을 얻었는데, Rapfi 사다리에서도 정확히 같은 구조가 다시 나타났어. 결정적 상대와의 측정에서 표본 크기를 늘리는 유일한 방법은 시작 다양성을 늘리는 거야.

            # pass if >= 2 of 3 pass -- one deterministic game per problem was too noisy
            trials = []
            for sims in TRIAL_SIMS:
                ...

생각해 볼 점. 결정적인 시스템에서 "노이즈"를 만들려면 입력을 흔들어야 해. 여기서는 탐색량(900/1100/1300)을 흔든 거야. 이건 "이 수가 특정 탐색량에서만 우연히 나온 게 아니라, 비슷한 탐색량에서 안정적으로 나오는가"를 보는 강건성 검사야. 로그에서 9/29 11:09 측정부터 trials_passed와 trials 필드가 나타나.

13.5 문제 하나씩

(1) 5수 필승 (web58_p5_attack)

58수 웹 대국의 30수 직후, X 차례. Rapfi가 찾은 해답 수순(solution_rapfi):

X (1,5) → O (2,5) → X (3,7) → O (5,9) → X (0,4)   # win_plies: 5

X가 3수를 더 두어 이기는 문제야. 마지막은 포크(동시에 두 개의 위협)로 끝나. 거의 모든 측정에서 3/3으로 통과했고, 첫 수는 대개 (1,5), 루트 가치 0.975였어. 10/1 05:32와 10:43의 snapshot은 첫 수가 (5,3), 가치 0.955로 다른 길을 찾았지만 역시 통과했어. 공격 문제는 "이기기만 하면" 통과라 다른 수순도 인정돼.

(2) 7수 필승 (web58_p7_attack)

같은 판 28수 직후, X 차례. X가 4수를 두어 이기는 문제, 일명 "7수 포크". 사람이 실제로 이 수순으로 모델을 이겼어. 5수 문제보다 두 수 더 멀리 봐야 해서, 탐색 트리 안에서 승리 수순이 충분히 일찍 발견되지 않으면 놓쳐. 9/29 05:45~11:09 사이 snapshot(ep600)은 0/3, ep620부터 3/3, ep700과 ep720은 다시 0/3. 모델에 따라 이 문제가 켜졌다 꺼졌다 했다는 게 흥미로워.

(3) 조용한 열린3 방어 (webB_quiet_three_defense)

problems.json의 note를 그대로 옮기면:

2026-09-28 15:56 web game (2000 sims): AI X played 21.(8,6); human 22.(4,8) made a quiet open three
in column 8 and won by 26. Value net rated the position after 22 at +0.998 for X while search proves
it lost. Rapfi 3s as X plays (4,8) itself and holds 40 plies (verified).

"조용한(quiet)" 수란 당장 4나 5를 만들지 않는, 위협처럼 보이지 않는 수야. 열린 3(양쪽이 막히지 않은 셋)은 다음 수에 열린 4가 되어 막을 수 없게 만들어. 문제는 가치망이 이 국면을 X에게 +0.998(거의 확실한 승리)로 봤다는 거야. 실제로는 진 국면인데. 가치망이 위험을 전혀 감지하지 못하는 "사각지대"야. 해법은 Rapfi처럼 X가 21수째에 상대의 핵심점 (4,8)을 먼저 차지하는 것.

이 문제의 출처 판은 "웹 판 B"라고 불렸어. 대화 기록에는 판 A와 판 B 두 패배를 비교하며 "둘 다 사람이 만든 세로줄을 AI가 막지 못해서 졌어"라고 분석한 대목이 있어.

(4) 13수 방어 (web58_d13_defense) — 2단계로 이동

After O's actual move 26 (8,9) Rapfi finds a forced X win in 13 plies; after move 25 no forced win
was found within 40 plies. A good O move 26 keeps the game open.

25수 직후 O 차례. 모델이 실제 대국에서 둔 (8,9)를 두면 13수짜리 필패 수순에 빠져. 판정은 "(8,9)를 두지 않고 40수 버티기". 13수 앞을 내다봐야 하는 매우 어려운 문제라서, 졸업 기준(stage 1)에서 빼서 stage 2 (장학금 문제)로 옮겼어. 졸업 선언문에도 "(장학금 문제) 13수 방어 3/3"으로 따로 적혀 있어. 9/30 이후 측정들에서는 대부분 0/3이야.

(5) 구석 대각선 (rapfi_cand3_diag_defense) — 관찰용

Observation only (stage 0, not a graduation criterion). From AI's loss vs Rapfi 300 nodes at

Rapfi 300노드와의 대국에서 진 판 32수 국면이야. 판 구석 쪽 대각선 위협을 못 봤어. 판의 가장자리와 구석은 학습 데이터에서 덜 나오는 영역이라 약할 가능성이 있다는 가설을 관찰하려고 넣었어. 졸업 기준은 아니야.

19. 확인하지 못한 것들

  • Rapfi의 11x11 신경망 비활성 여부는 대화 기록의 설명에 근거했어. Rapfi 출력 원문에서 직접 확인하지는 않았어.
  • 사다리 snapshot들이 정확히 어느 epoch의 best인지는 로그에 없어. 일부(ep555, ep580, ep600)는 대화 기록에서 대응시켰어.
  • 사람 상대 "약 88%"라는 수치는 games.jsonl로 재현하지 못했어(현재 파일: 승률 90.2%, 점수 92.6%; 졸업 시점 README: 83%).
  • 20판 안에서 실제로 서로 다른 판이 몇 개인지(같은 시작+색 조합의 반복 판이 동일 수순이었는지)는 수순 비교로 확인하지 않았어.
  • 게이트 표의 epoch 번호는 로그상 직전 Epoch 줄로 대응시킨 거야.
  • 사다리 동시 실행에 의한 매치 로그 혼입 사고가 있었는지는 확인하지 못했어.
