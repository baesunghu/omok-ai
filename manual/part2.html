0. 들어가며: 이 부를 읽는 법과 파일 지도

1부에서 AlphaZero의 개념(정책망, 가치망, MCTS, 자기대국)을 원리 수준에서 봤다면, 2부는 그 개념이 이 프로젝트 코드에서 실제로 어느 줄에 어떻게 구현돼 있는지를 한 줄씩 따라가는 부분이야. 인용한 코드는 모두 2026-10-06 기준 저장소의 실제 파일에서 그대로 옮겼고, 생략한 곳은 ...로 표시했어. 숫자(파라미터 수, 상수값)는 코드에서 직접 읽었거나 코드를 보고 손으로 계산한 거야. 계산한 숫자는 계산 과정도 같이 적었어.

읽는 순서 추천. 이 부는 "바닥에서 위로" 순서로 짜여 있어. 판 표현(1~2장) → 신경망(3장) → 탐색 엔진(4~8장) → 병렬 대국(9장) → 학습 루프(10~14장) → 설정(15장). 각 장이 앞 장의 개념을 쓰니까 처음이라면 순서대로 읽는 걸 권해. 아는 부분은 건너뛰어도 되지만, 7장의 가상 손실 부호 버그와 14장의 학습 스텝은 꼭 읽어 봐.

0.2 공통 표기

  • 판 표현이 세 가지 공존해. (1) 파이썬 리스트의 리스트. 칸 값은 문자열 'X', 'O', ' '야. (2) C++/numpy용 정수 배열(int8). 0=빈칸, 1=X, 2=O. (3) fast_board의 Numba용 정수 배열(int32). 1=X, -1=O.
  • 행동 번호(action index): 칸 (r, c)는 r * 11 + c, 즉 0~120 사이 정수 하나로 표현돼. 거꾸로 바꿀 땐 divmod(act, 11).
  • ply: 한 사람이 돌 하나를 둔 것. 이 글에서는 "수"와 같은 뜻으로 쓸게.
  • mover: 지금 둘 차례인 사람. 이 코드의 가치(value)는 항상 "그 노드에서 둘 차례인 사람 입장"에서 매겨져. 이 관점 규칙 때문에 MCTS 코드 곳곳에서 부호(+/−)가 뒤집혀.
  • X가 항상 선수: 빈 판에서 시작하는 게이트·리그 대국은 current_player = 'X'로 시작해. 단, 자기대국은 random.choice(['X','O'])로 시작 색을 무작위로 골라(10장 참고).

1. fast_board.py — 승리 판정의 가장 밑바닥

게임 규칙을 코드로 옮긴 가장 원시적인 층이야. 오목(자유룰, freestyle)에서 "이겼나?"는 "같은 색 돌이 가로·세로·두 대각선 중 한 방향으로 5개 이상 연속인가?"라는 질문이야. 6목(장목)도 승리로 치는 게 자유룰이고, 이 코드도 그래. 6개가 이어져 있으면 그 안에 5개 연속이 있으니까 자동으로 승리로 처리돼.

  2. 기본 인자 board_size=5, win_len=3은 옛날 5×5/3목 시절의 흔적이야. 실제 호출부(fast_check_win)가 항상 BOARD_SIZE, WIN_LENGTH(11, 5)를 명시적으로 넘기니까 문제는 없어.
  3. 모든 칸 (r, c)를 돌면서 그 칸에 해당 플레이어 돌이 있을 때만 그 칸을 "시작점"으로 4방향을 검사해. 8방향이 아니라 4방향만 보는 이유는, 반대 방향은 "다른 시작점에서 출발한 같은 줄"이라 중복이기 때문이야. 왼쪽으로 이어진 5목은 그 줄의 가장 왼쪽 돌에서 오른쪽으로 보면 찾을 수 있지.
  4. if c <= board_size - win_len: 오른쪽으로 4칸 더 가도 판 밖으로 안 나가는지 보는 경계 검사야. 11−5=6이니까 c가 0~6일 때만 가로 검사를 해.
  5. 왼쪽 아래 대각선(/ 방향)은 c >= win_len - 1, 즉 c가 4 이상이어야 왼쪽으로 4칸 더 갈 수 있어.

비용 감각. 121칸 × 4방향 × 최대 4번 비교면 대략 2,000번 비교야. 아주 싸 보이지만, 이 판정은 대국 중 매 수마다, 채굴 단계에서는 후보 칸마다 불려. 무거운 탐색 내부의 판정은 C++ 엔진이 같은 로직(4장의 check_win)으로 직접 해.

2. alphago_lee.py — 판을 숫자로 바꾸기

신경망은 "판"을 모르고 숫자 텐서만 알아. 이 장은 11×11 판이 신경망 입력 (5, 11, 11) float32 텐서로 바뀌는 과정을 다뤄. 5장의 평면(plane) 중 3장은 그냥 "어디에 뭐가 있나"이고, 나머지 2장은 이 프로젝트의 특징인 포크(쌍삼/사삼류 이중 위협) 탐지 평면이야.

2.2 _generate_lines — "5칸짜리 창문" 전부 나열하기

def _generate_lines():
    lines = []
    max_start = BOARD_SIZE - WIN_LENGTH

    # Horizontal windows
    for r in range(BOARD_SIZE):
        for c in range(max_start + 1):
            lines.append([(r, c + k) for k in range(WIN_LENGTH)])

    # Vertical windows
    for c in range(BOARD_SIZE):
        for r in range(max_start + 1):
            lines.append([(r + k, c) for k in range(WIN_LENGTH)])

    # Diagonal windows (down-right, "\")
    for r in range(max_start + 1):
        for c in range(max_start + 1):
            lines.append([(r + k, c + k) for k in range(WIN_LENGTH)])

    # Diagonal windows (down-left, "/")
    for r in range(max_start + 1):
        for c in range(WIN_LENGTH - 1, BOARD_SIZE):
            lines.append([(r + k, c - k) for k in range(WIN_LENGTH)])

    return lines

창문(window)이란 연속한 5칸 묶음이야. 5목은 반드시 어떤 창문 하나를 같은 색으로 꽉 채우는 것이니까, 창문 목록만 있으면 승리·위협 판정을 "창문마다 돌이 몇 개냐"는 셈으로 바꿀 수 있어.

11×11에서 창문 개수를 직접 세 보자. max_start = 11−5 = 6이니까 한 줄에 시작점이 0~6, 7개야.

2.3 _immediate_win_mask — "지금 두면 5목이 되는 칸"

def _immediate_win_mask(curr_plane, empty_plane):
    curr_flat = curr_plane.ravel()
    empty_flat = empty_plane.ravel()
    line_curr = curr_flat[_LINES_IDX]
    line_empty = empty_flat[_LINES_IDX]
    curr_counts = line_curr.sum(axis=1)
    empty_counts = line_empty.sum(axis=1)
    hit = (curr_counts == WIN_LENGTH - 1) & (empty_counts == 1)
    mask = np.zeros(BOARD_SIZE * BOARD_SIZE, dtype=np.float32)
    if hit.any():
        hit_lines = _LINES_IDX[hit]
        hit_empty = line_empty[hit]
        slot = hit_empty.argmax(axis=1)
        target = hit_lines[np.arange(len(slot)), slot]
        mask[target] = 1.0
    return mask.reshape(BOARD_SIZE, BOARD_SIZE)
  1. ravel(): (11,11)을 (121,)로 펼쳐. 복사 없이 뷰를 주는 경우가 많아.
  2. line_curr: (252, 5). 각 창문의 5칸이 내 돌(1.0)인지 아닌지(0.0).
  3. curr_counts, empty_counts: 창문마다 내 돌 수, 빈칸 수.
  4. hit: 내 돌 4개 + 빈칸 1개인 창문. 상대 돌이 하나라도 있으면 4+1=5를 못 채우니까 자동으로 걸러져.
  5. slot = hit_empty.argmax(axis=1): 그 창문의 5칸 중 빈칸이 몇 번째인지. 빈칸은 1.0, 나머지는 0.0이니까 argmax가 곧 빈칸 위치야.
  6. target: 그 빈칸의 1차원 칸 번호. mask[target] = 1.0으로 표시해.

이 함수는 현재 _fork_mask_python 안에서 같은 로직이 다시 쓰이고 있어("baseline" 부분). 지금 학습 경로가 직접 이 함수를 부르지는 않아.

2.4 _fork_mask — 포크 평면의 정의

먼저 포크(fork)의 정의를 코드 그대로 옮기면 이래.

빈칸 A에 내 돌을 놓았을 때, "다음 수에 두면 5목이 되는 서로 다른 빈칸"이 2개 이상 생기면 A는 포크 칸이다.

왜 중요하냐면, 5목 완성 칸이 2개면 상대는 한 수에 하나밖에 못 막으니까 막을 수 없는 승리가 되거든. 오목 용어로는 4-4, 4-3에서 4가 두 개 생기는 상황이나, 다음 수에 열린 4(양쪽이 빈 4)를 만드는 상황의 "한 단계 전"이야. 엄밀히 말하면 이 마스크는 "다음 수에 바로 이기는 칸이 2개 이상"만 보니까 4-4 / 4-열린4 류만 잡고, 3-3(열린 삼 두 개)은 직접 잡지 않아. 3-3은 한 수 더 깊은 위협이라서 이 평면이 아니라 신경망과 탐색이 배워야 해.

try:
    import fork_mask_cpp as _fork_mask_native
except ImportError:
    _fork_mask_native = None

def _fork_mask(curr_plane, empty_plane):
    if _fork_mask_native is not None:
        return _fork_mask_native.fork_mask(curr_plane, empty_plane)
    return _fork_mask_python(curr_plane, empty_plane)

디스패처야. 컴파일된 C++ 확장 fork_mask_cpp.pyd(10x10 폴더에 실제로 있음)가 있으면 그걸 쓰고, 없으면 파이썬 구현을 써. 주석에 따르면 2026-09-16에 numba / 완전 벡터화 numpy / C++ / 비트보드 4가지를 벤치마크했고, C++과 numba가 약 9~11배로 동률이었는데 프로젝트 관례(컴파일 엔진 + 파이썬 폴백)에 맞춰 C++을 골랐어. 두 구현은 "374개 보드에서 바이트 단위로 동일"하다고 검증됐다고 적혀 있어.

2.5 _fork_mask_python — O(창문 수) 알고리즘 한 줄씩

순진한 방법은 "빈칸마다 돌을 놓아 보고, 판 전체에서 5목 완성 칸을 다시 센다"야. 빈칸 ~100개 × 창문 252개 = 매번 2만 5천 번 셈이고, 이게 탐색 시뮬레이션마다 두 번(fork_self, fork_opp) 불려. 주석에 따르면 이 방식일 때 포크 탐지가 전체 시뮬레이션 시간의 ~60%였대. 그래서 수학적 관찰 하나로 창문 수에 비례하는 알고리즘으로 바꿨어.

핵심 관찰. 빈칸 A에 돌을 놓을 때 새로 생길 수 있는 "5목 완성 칸"은, A를 포함하면서 지금 내 돌 3개 + 빈칸 2개(그중 하나가 A)인 창문에서만 나와. A를 채우면 그 창문은 내 돌 4개 + 빈칸 1개가 되고, 남은 빈칸 B가 새 완성 칸이 되지. 반대로 이미 4+1인 창문이 A를 지나간다면 그 창문의 빈칸은 A 자신이니까, A를 놓으면 그 창문은 그냥 5목(즉시 승리)이 되고 "완성 칸 목록"에서는 A가 빠져.

    L = WIN_LENGTH
    n_cells = BOARD_SIZE * BOARD_SIZE
    curr_flat = curr_plane.ravel()
    empty_flat = empty_plane.ravel()
    line_curr = curr_flat[_LINES_IDX]
    line_empty = empty_flat[_LINES_IDX]
    curr_counts = line_curr.sum(axis=1)
    empty_counts = line_empty.sum(axis=1)

    baseline_arr = np.zeros(n_cells, dtype=np.int32)
    baseline_hit = (curr_counts == L - 1) & (empty_counts == 1)
    if baseline_hit.any():
        hit_lines = _LINES_IDX[baseline_hit]
        hit_empty = line_empty[baseline_hit]
        slot = hit_empty.argmax(axis=1)
        targets = hit_lines[np.arange(len(slot)), slot]
        baseline_arr[targets] = 1  # set-like dedup: plain assignment, not +=
    baseline_count = int(baseline_arr.sum())

1단계(baseline): 아무것도 안 놓은 지금 이미 존재하는 5목 완성 칸 집합을 0/1 배열로 만들어. baseline_arr[targets] = 1에서 +=가 아니라 =를 쓴 게 중요해. 같은 칸이 두 창문에서 완성 칸이어도 1로만 세서 집합처럼 중복을 없애는 거야. baseline_count는 그 집합의 크기.

    threat_count = np.zeros(n_cells, dtype=np.int32)
    overlap = np.zeros(n_cells, dtype=np.int32)
    two_empty_lines = np.where((curr_counts == L - 2) & (empty_counts == 2))[0]
    threats = {}
    for li in two_empty_lines:
        positions = np.where(line_empty[li] > 0)[0]
        a_idx = int(_LINES_IDX[li, positions[0]])
        b_idx = int(_LINES_IDX[li, positions[1]])
        threats.setdefault(a_idx, set()).add(b_idx)
        threats.setdefault(b_idx, set()).add(a_idx)
    for a, s in threats.items():
        threat_count[a] = len(s)
        if baseline_count:
            overlap[a] = sum(1 for b in s if baseline_arr[b])

2단계(새 위협): 내 돌 3 + 빈칸 2인 창문을 찾아서 두 빈칸 a, b를 짝지어. "a를 두면 b가 새 완성 칸", "b를 두면 a가 새 완성 칸"이니까 양방향으로 기록해. threats[a]는 "a를 두면 새로 생기는 완성 칸들의 집합"이야(set이라 중복 제거).

overlap[a]는 그 새 완성 칸들 중 이미 baseline에 있던 칸 수야. 이미 있던 칸을 "새로" 셀 수는 없으니까 빼 줘야 해.

    total = baseline_count - baseline_arr + threat_count - overlap
    mask = ((total >= 2) & (empty_flat > 0)).astype(np.float32)
    return mask.reshape(BOARD_SIZE, BOARD_SIZE)

3단계(합치기): A에 두었을 때 완성 칸 집합의 크기는

|(baseline − {A}) ∪ T(A)| = baseline_count − [A ∈ baseline] + |T(A)| − |T(A) ∩ baseline|

이고, 이걸 121칸 전부에 대해 numpy 배열 연산 한 줄로 계산한 게 total이야. (A는 자기 위협 집합 T(A)에 절대 안 들어가니까 이 항등식이 성립해. docstring에도 이 조건이 적혀 있어.) total >= 2이고 A가 빈칸이면 포크 칸이야.

손으로 돌려 보는 예

X 입장에서 다음 판을 생각해 보자(가운데 부분만 표시, .=빈칸).

     c: 2 3 4 5 6
r=5     . X X X .      ← 가로: (5,3)(5,4)(5,5)에 X
r=6     . . . . .
r=7     . . . . .

가로 창문 [(5,2)…(5,6)]은 X 3개 + 빈칸 2개 [(5,2),(5,6)]야. 그러니까 threats[(5,2)] ∋ (5,6), threats[(5,6)] ∋ (5,2). 창문 [(5,1)…(5,5)]도 X 3개 + 빈칸 (5,1),(5,2)라서 threats[(5,2)] ∋ (5,1)이 추가돼. 창문 [(5,3)…(5,7)]도 같은 식으로 threats[(5,6)] ∋ (5,7)이 추가되고.

  • (5,2)에 X를 두면: 새 완성 칸 {(5,6), (5,1)} → 2개 → 포크! (실제로 (5,2)~(5,5)가 열린 4가 돼서 양쪽 끝 (5,1), (5,6) 둘 다 승리 칸이야.)
  • (5,6)에 두면: {(5,2), (5,7)} → 역시 포크.
  • (5,1)에 두면: 창문 [(5,1)…(5,5)]에서만 → {(5,2)} → 1개 → 포크 아님(띈 4, 막을 수 있어).

즉 이 판에서 fork_self 평면은 (5,2), (5,6)에 1.0이 찍혀. 이건 "열린 3을 열린 4로 만드는 칸"과 정확히 같지. 신경망은 이걸 계산하지 않고 입력으로 공짜로 받는 셈이야. 상대 입장에서 같은 계산을 한 게 fork_opp 평면이고, 이건 "막지 않으면 상대가 다음 수에 막을 수 없는 위협을 만드는 칸" 정보가 돼.

한계. 이 마스크는 "놓으면 승리 칸이 2개 이상"만 봐. 그래서 (1) 3-3 포크(열린 3 두 개, 승리까지 두 수)는 안 잡히고, (2) 상대가 그 완성 칸을 막으면서 동시에 자기 4를 만드는 반격 같은 건 고려하지 않아. 이건 분석적(규칙 기반) 특징일 뿐이고 정답이 아니야. 나머지는 신경망과 탐색 몫이야. 실제로 3-3(T자) 형태 포크는 프로젝트 후반까지 약점으로 남았어(13장 Hard-7, 메모리 노트의 T-shape 측정 참고).

2.6 board_to_input_array — 문자열 판에서 5장 평면

def board_to_input_array(board_state, current_player):
    arr = np.array(board_state)
    opponent_player = 'O' if current_player == 'X' else 'X'
    curr_plane = (arr == current_player).astype(np.float32)
    opp_plane = (arr == opponent_player).astype(np.float32)
    empty_plane = (arr == ' ').astype(np.float32)
    fork_self = _fork_mask(curr_plane, empty_plane)
    fork_opp = _fork_mask(opp_plane, empty_plane)
    return np.stack([curr_plane, opp_plane, empty_plane, fork_self, fork_opp])

5장의 순서가 고정 계약이야: [curr, opp, empty, fork_self, fork_opp].

채널이름의미
0curr지금 둘 차례인 사람의 돌 = 1
1opp상대 돌 = 1
2empty빈칸 = 1
3fork_self내가 두면 포크가 되는 칸 = 1
4fork_opp상대가 두면 포크가 되는 칸 = 1

여기서 중요한 설계 결정은 "X/O"가 아니라 "나/상대"로 표현한다는 거야. 그래서 네트워크는 "지금 내가 흑인지 백인지"를 몰라. 같은 모양이면 같은 판단을 하게 되고, 데이터 효율이 두 배가 되지. 대신 "누가 선수인가"라는 정보는 입력에 직접 없어. 돌 개수 차이(curr 수 vs opp 수)로 간접적으로 알 수는 있어.

이 함수는 학습 샘플을 저장할 때(10장 board_3d = board_to_input_array(board, current_player))와 하드 예제를 만들 때 쓰여.

3.1 V1 (역사): Conv + BatchNorm 잔차 블록

class ResBlock(nn.Module):
    def __init__(self, channels=64):
        super(ResBlock, self).__init__()
        self.conv1 = nn.Conv2d(channels, channels, kernel_size=3, padding=1)
        self.bn1 = nn.BatchNorm2d(channels)
        self.relu = nn.ReLU(inplace=True)
        self.conv2 = nn.Conv2d(channels, channels, kernel_size=3, padding=1)
        self.bn2 = nn.BatchNorm2d(channels)

    def forward(self, x):
        residual = x
        out = self.relu(self.bn1(self.conv1(x)))
        out = self.bn2(self.conv2(out))
        out += residual
        return self.relu(out)

기본 개념부터 짚고 가자.

  • Conv2d(C, C, 3, padding=1): 각 칸에서 주변 3×3 영역의 C개 채널 값을 가중합해 새 C개 채널을 만들어. padding=1은 판 가장자리 밖을 0으로 채워서 출력도 11×11로 유지하는 거야. 3×3 합성곱을 층마다 쌓으면 "보는 범위(receptive field)"가 층마다 2칸씩 넓어져. 5목을 보려면 최소 5칸 범위가 필요하고, 판 전체(11칸)를 보려면 합성곱 5~6층이 필요해.
  • 잔차 연결(residual): out += residual. 블록이 "입력에 더할 보정량"만 배우게 해서, 깊은 네트워크도 학습이 잘 돼(ResNet의 핵심 아이디어).
  • BatchNorm: 배치 전체의 평균/분산으로 정규화해. 문제는 train 모드와 eval 모드의 동작이 다르다는 거야. train 모드에서는 지금 배치의 통계를 쓰는데, MCTS가 판 하나(배치 1)만 넣으면 그 판 하나의 통계로 정규화돼서 출력이 엉망이 돼. 이 프로젝트는 이 버그를 실제로 겪었어(게이트 체크에서 model.eval()을 빼먹은 사건, 2026-08-29. run_gating_check 안의 주석 참고).

3.2 V2: GroupNorm + SE (alphago_lee_v2_seblock.py)

V2는 위 문제를 근본적으로 없애려고 정규화를 GroupNorm으로 바꾸고, SE(Squeeze-and-Excitation) 채널 게이트를 추가했어.

(a) _group_norm

def _group_norm(channels, max_groups=32):
    groups = min(max_groups, channels)
    while channels % groups != 0:
        groups -= 1
    return nn.GroupNorm(groups, channels)

GroupNorm은 채널을 그룹으로 나눠서 샘플 하나 안에서 평균/분산을 구해 정규화해. 배치 크기나 train/eval 모드와 상관없이 항상 같은 계산이야. 256채널이면 32그룹(그룹당 8채널), 8채널이면 8그룹, 4채널이면 4그룹, 2채널이면 2그룹이 돼. while 루프는 채널 수가 32로 나누어떨어지지 않을 때 나누어떨어지는 가장 큰 그룹 수를 찾는 안전장치야.

(b) SEBlock

class SEBlock(nn.Module):
    def __init__(self, channels, reduction=16):
        super().__init__()
        reduced = max(1, channels // reduction)
        self.pool = nn.AdaptiveAvgPool2d(1)
        self.fc1 = nn.Conv2d(channels, reduced, kernel_size=1)
        self.relu = nn.ReLU(inplace=True)
        self.fc2 = nn.Conv2d(reduced, channels, kernel_size=1)
        self.sigmoid = nn.Sigmoid()

    def forward(self, x):
        s = self.pool(x)
        s = self.relu(self.fc1(s))
        s = self.sigmoid(self.fc2(s))
        return x * s
  1. Squeeze: AdaptiveAvgPool2d(1)가 채널마다 11×11 전체를 평균해서 숫자 하나로 만들어. (B, 256, 11, 11) → (B, 256, 1, 1). "이 특징이 판 전체에서 얼마나 활성인가"야.
  2. Excitation: 256 → 16 → 256의 작은 병목 MLP(1×1 합성곱이 곧 완전연결층이야)를 지나 sigmoid로 0~1 게이트 256개를 만들어.
  3. x * s: 채널마다 그 게이트 값을 곱해. 판 전체 맥락을 보고 "지금 이 판에선 이 특징 채널을 키우고 저 채널은 줄이자"를 동적으로 정하는 거야. 일반 합성곱은 3×3 국소 정보만 보니까, 전역 정보를 싸게 주입하는 장치라고 보면 돼. KataGo도 비슷한 전역 풀링을 써.

(c) DSConv — 이름만 남은 평범한 합성곱

class DSConv(nn.Module):
    """2026-09-21: depthwise/grouped separable convs were tried (full
    depthwise, then groups=32) and both measured far SLOWER wall-clock on
    this GPU than a standard conv despite fewer FLOPs -- grouped conv
    benchmarked at 18.75s/train-step (batch 256) vs the original
    architecture's ~0.78s/step, a ~24x regression. ..."""
    def __init__(self, in_channels, out_channels):
        super().__init__()
        self.conv = nn.Conv2d(in_channels, out_channels, kernel_size=3, padding=1)
        self.norm = _group_norm(out_channels)

    def forward(self, x):
        x = self.conv(x)
        x = self.norm(x)
        return x

이름은 "Depthwise-Separable Conv"인데 실제로는 평범한 3×3 합성곱 + GroupNorm이야. 깊이별 분리 합성곱은 계산량(FLOPs)은 8~9배 적지만, 이 오래된 GPU에서는 메모리 대역폭 병목 때문에 오히려 약 24배 느렸어(학습 스텝 18.75초 vs 0.78초). 그래서 되돌렸고, 클래스 이름은 코드 변경을 줄이려고 그대로 뒀어. "FLOPs가 적으면 빠르다"는 직관이 하드웨어에 따라 틀릴 수 있다는 좋은 교훈이야.

(d) FusedSEResBlock

class FusedSEResBlock(nn.Module):
    def __init__(self, channels, se_reduction=16):
        super().__init__()
        self.conv1 = DSConv(channels, channels)
        self.relu = nn.ReLU(inplace=True)
        self.conv2 = DSConv(channels, channels)
        self.se = SEBlock(channels, reduction=se_reduction)

    def forward(self, x):
        residual = x
        out = self.relu(self.conv1(x))
        out = self.conv2(out)
        out = self.se(out)
        out = out + residual
        return self.relu(out)

흐름: 합성곱→GN→ReLU → 합성곱→GN → SE 게이트 → 입력 더하기 → ReLU. V1과 비교하면 BN이 GN으로 바뀌고, 잔차를 더하기 직전에 SE가 들어간 거야. 그 밖의 구조는 같아.

            if (r <= BOARD_SIZE - WIN_LENGTH && c >= WIN_LENGTH - 1) { ... / ... }
        }
    }
    return false;
}

static bool check_draw(const std::vector<int8_t>& b) {
    for (auto v : b) if (v == 0) return false;
    return true;
}

fast_board.py와 완전히 같은 알고리즘이야. 판은 길이 121의 1차원 vector<int8_t>이고, (r, c)는 r*BOARD_SIZE + c로 접근해. static은 이 함수를 이 파일 안에서만 보이게 하는 C++ 키워드야.

4.3 relevant_cells — 반경 2 이웃 가지치기

11×11 판에서 빈칸은 최대 121개야. 이 전부를 후보 수로 펼치면 트리가 너무 넓어져서 같은 시뮬레이션 수로도 수읽기가 얕아져. 오목에서는 기존 돌에서 멀리 떨어진 수는 거의 의미가 없다는 도메인 지식을 써서 후보를 줄여.

static const int NEIGHBOR_RADIUS = 2;

static std::vector<int> relevant_cells(const std::vector<int8_t>& b, int BOARD_SIZE) {
    std::vector<int> occupied;
    occupied.reserve(b.size());
    for (int i = 0; i < (int)b.size(); i++) {
        if (b[i] != 0) occupied.push_back(i);
    }

    if (occupied.empty()) {
        int mid = BOARD_SIZE / 2;
        std::vector<int> center;
        center.push_back((mid - 1) * BOARD_SIZE + (mid - 1));
        center.push_back((mid - 1) * BOARD_SIZE + mid);
        center.push_back(mid * BOARD_SIZE + (mid - 1));
        center.push_back(mid * BOARD_SIZE + mid);
        return center;
    }

    std::vector<char> seen(b.size(), 0);
    std::vector<int> relevant;
    for (int idx : occupied) {
        int r0 = idx / BOARD_SIZE, c0 = idx % BOARD_SIZE;
        int rlo = std::max(0, r0 - NEIGHBOR_RADIUS), rhi = std::min(BOARD_SIZE - 1, r0 + NEIGHBOR_RADIUS);
        int clo = std::max(0, c0 - NEIGHBOR_RADIUS), chi = std::min(BOARD_SIZE - 1, c0 + NEIGHBOR_RADIUS);
        for (int r = rlo; r <= rhi; r++) {
            for (int c = clo; c <= chi; c++) {
                int j = r * BOARD_SIZE + c;
                if (b[j] == 0 && !seen[j]) {
                    seen[j] = 1;
                    relevant.push_back(j);
                }
            }
        }
    }

    if (relevant.empty()) {
        std::vector<int> all_empty;
        for (int i = 0; i < (int)b.size(); i++) if (b[i] == 0) all_empty.push_back(i);
        return all_empty;
    }
    return relevant;
}
  1. 빈 판: 놓인 돌이 없으면 "중앙 2×2" 네 칸을 돌려줘. mid = 11/2 = 5니까 (4,4), (4,5), (5,4), (5,5)야. 주의할 점: 11×11의 진짜 정중앙은 (5,5) 한 칸인데, 이 규칙은 짝수 판(10×10) 시절에 만든 거라 (5,5)를 포함하는 2×2가 돼. 빈 판에서 엔진이 첫 수를 두면 이 4칸 중 하나야. (게이트·리그 대국은 첫 수를 강제 오프닝으로 두니까 이 규칙을 안 타. 자기대국 첫 수는 이걸 타.)
  2. 체비셰프 거리 2: 돌마다 가로세로 ±2, 즉 5×5 정사각형 안의 빈칸을 모아. 대각선 5목도 가로세로만큼 중요하니까 원(유클리드)이 아니라 정사각형을 써.
  3. seen: 여러 돌의 이웃이 겹치니까 중복을 막는 표시 배열이야.
  4. 안전망: 이웃에 빈칸이 하나도 없는데 판에 빈칸은 있는 경우(이론상 거의 불가능)엔 전체 빈칸을 돌려줘. 가지치기 버그가 "둘 곳 없음 = 무승부"로 둔갑하는 걸 막는 방어 코드야.

후보 수 감각

돌 1개면 후보는 5×5−1 = 24칸이야. 돌이 몇 개 모이면 대략 30~50칸이 돼. make_lrfix의 주석은 "radius-2 candidate set (~45 cells)"이라고 적고 있어. 121칸 대비 1/3 정도라서 같은 시뮬레이션 수로 훨씬 깊게 읽을 수 있어.

   . o o o o o .       o = 후보 (돌 ● 하나 기준, 반경 2)
   . o o o o o .
   . o o ● o o .
   . o o o o o .
   . o o o o o .
   . . . . . . .

가지치기의 대가. 반경 2 밖의 수는 아예 고려되지 않아. 오목에서 이게 문제 되는 경우는 드물지만 0은 아니야. 예를 들어 멀리 떨어진 "준비 수"는 엔진이 절대 못 둬. Solver 주석은 "ALL children means all children in the neighbor-radius candidate set, which always contains every cell adjacent to a stone -- the only cells that can complete a five or block one"이라고 정당화해. 5목을 완성하거나 막는 칸은 항상 기존 돌에 인접(거리 1)하니까, 즉시 승패에 관해서는 반경 2 후보 집합이 완전하다는 거지. 단, 여러 수 앞의 전략에 대해서는 완전하지 않아.

4.4 메이트 거리 (mate_scaled)

static const double MATE_DISTANCE_ALPHA = 0.005;
static const double MATE_DISTANCE_FLOOR = 0.5;

static double mate_scaled(double v, int depth) {
    double mag = 1.0 - MATE_DISTANCE_ALPHA * depth;
    if (mag < MATE_DISTANCE_FLOOR) mag = MATE_DISTANCE_FLOOR;
    return v * mag;
}

MCTS가 게임 끝(5목)에 도달하면 원래는 ±1을 역전파해. 그런데 후수가 거의 항상 지는 이 게임에서는 후수 입장의 모든 수가 결국 −1이라, 탐색이 "더 오래 버티는 수"를 선호할 이유가 없었어. 체스 엔진의 "mate in N" 점수처럼, 루트에서 깊이 d에서 끝난 결과를 1 − 0.005·d배로 줄여.

루트에서 깊이승리 값패배 값
1+0.995−0.995
5+0.975−0.975
20+0.900−0.900
100 이상+0.500 (하한)−0.500 (하한)

효과: 이기는 쪽은 더 빨리 이기는 수를, 지는 쪽은 더 늦게 지는 수를 조금 더 좋게 봐. 하한 0.5는 아주 깊은 강제승도 확실한 승리로 보이게 하는 장치야. 주석에 적힌 작은 부정확성도 있어: 트리 재사용으로 루트가 1~2수 내려가도, 재사용된 서브트리에 이미 저장된 값은 옛 루트 기준 깊이로 줄어든 상태야. "작은 균일 오프셋"이라 단순함을 위해 감수했대.

5. C++ 엔진 (2) — MCTS-Solver: 증명된 승패

2026-09-27에 추가된 기능이야. 주석의 동기를 옮기면:

일반 MCTS는 평균을 내. 상대가 다음 수에 바로 5목을 만들 수 있는 수(=안 막는 수)를 뒀을 때도, 그 자식의 Q는 −0.86 정도밖에 안 됐어. 상대의 응수 중 이기는 수는 하나뿐이고 나머지는 평범한 값이라 평균이 희석되거든. 그런데 가치망이 "막는 수"도 −0.9로 잘못 평가하면(ep470 측정) 탐색이 막는 수와 안 막는 수를 구별하지 못해서, 고정 테스트 20개 중 3개에서 즉시 4를 안 막았어.

해결책은 Winands, Björnsson & Saito(2008)의 MCTS-Solver야. 승패가 확정된 노드는 평균이 아니라 미니맥스로 올려 보내.

5.1 wins_at — 한 칸에 두면 5목인가

static bool wins_at(const std::vector<int8_t>& b, int idx, int player, int BOARD_SIZE, int WIN_LENGTH) {
    const int r0 = idx / BOARD_SIZE, c0 = idx % BOARD_SIZE;
    static const int DR[4] = {0, 1, 1, 1};
    static const int DC[4] = {1, 0, 1, -1};
    for (int d = 0; d < 4; d++) {
        int count = 1;
        for (int sgn = -1; sgn <= 1; sgn += 2) {
            int r = r0 + sgn * DR[d], c = c0 + sgn * DC[d];
            while (r >= 0 && r < BOARD_SIZE && c >= 0 && c < BOARD_SIZE && b[r * BOARD_SIZE + c] == player) {
                count++;
                r += sgn * DR[d];
                c += sgn * DC[d];
            }
        }
        if (count >= WIN_LENGTH) return true;
    }
    return false;
}

전체 판을 다 훑는 check_win과 달리, 놓을 칸 하나를 중심으로 4방향 × 양쪽으로 같은 색이 몇 개 이어지는지 셈해. 놓을 돌 자신이 1이고(count = 1), 양쪽으로 뻗으며 더해서 5 이상이면 승리야. 비용이 작아서 노드를 펼칠 때마다 모든 후보 칸에 불러도 돼.

5.2 update_proof — 자식들로부터 내 증명 다시 계산

static bool update_proof(Node* node) {
    if (node->proven != 0 || !node->is_expanded || node->children.empty()) return false;
    int best_win = -1;
    bool all_lose = true;
    int worst_loss = 0;
    for (auto& kv : node->children) {
        Node* ch = kv.second.get();
        if (ch->proven == -1) {
            int d = ch->proof_dist + 1;
            if (best_win < 0 || d < best_win) best_win = d;
        }
        if (ch->proven != 1) {
            all_lose = false;
        } else {
            int d = ch->proof_dist + 1;
            if (d > worst_loss) worst_loss = d;
        }
    }
    if (best_win >= 0) { node->proven = 1; node->proof_dist = best_win; return true; }
    if (all_lose) { node->proven = -1; node->proof_dist = worst_loss; return true; }
    return false;
}

규칙은 미니맥스 그대로야(관점에 주의!).

  • 자식 하나라도 proven == -1(자식 국면에서 둘 사람, 즉 상대가 지는 게 증명됨)이면 → 나는 그 수를 두면 이겨 → 나는 승리 증명(+1). 거리는 가장 빠른 승리 min(자식 거리 + 1).
  • 모든 자식이 proven == 1(상대가 이기는 게 증명됨)이면 → 뭘 둬도 져 → 나는 패배 증명(−1). 거리는 가장 늦은 패배 max(자식 거리 + 1). 지는 쪽은 최대한 버틴다고 가정하는 거야.
  • 그 밖에는 모름(0).

첫 줄의 조건에서 보이듯 증명은 한 번 정해지면 절대 취소되지 않아(0 → ±1로만 바뀜). 그래서 proven != 0이면 바로 false를 돌려줘.

5.3 propagate_proof — 위로 퍼뜨리기

static void propagate_proof(Node* node) {
    Node* p = node->parent;
    while (p != nullptr && update_proof(p)) p = p->parent;
}

한 노드의 증명이 바뀌면 부모도 바뀔 수 있으니 위로 올라가며 다시 계산해. 어떤 조상이 "안 바뀌면" 그 위는 볼 필요가 없으니 멈춰.

5.4 mark_immediate_wins — 펼칠 때 즉시 승리 표시

static void mark_immediate_wins(Node* node, const std::vector<int8_t>& b, int player, int BOARD_SIZE, int WIN_LENGTH) {
    for (auto& kv : node->children) {
        if (wins_at(b, kv.first, player, BOARD_SIZE, WIN_LENGTH)) {
            kv.second->proven = -1;      // the child's mover (opponent) has lost
            kv.second->proof_dist = 0;
        }
    }
    if (update_proof(node)) propagate_proof(node);
}

노드를 펼칠 때(자식을 만들 때) 후보 칸마다 "지금 둘 사람이 여기 두면 5목인가"를 검사해. 5목이면 그 자식 국면은 이미 끝난 판이고, 그 국면에서 둘 차례인 상대는 졌으니 자식을 proven = -1, proof_dist = 0으로 표시해. 그리고 update_proof를 부르면 부모(지금 노드)는 자동으로 "승리 증명, 거리 1"이 돼.

예시로 따라가기

국면 A (X 차례): X가 (5,2)에 두면 5목.
  expand(A) → 자식 (5,2): proven=-1, dist=0   (O가 진 판)
            → update_proof(A): best_win = 0+1 = 1 → A.proven=+1, dist=1
            → propagate: A의 부모 P(O 차례)는 자식 A가 proven=+1(X가 이김)
               → P의 자식이 "전부" +1인지는 다른 자식에 달림. 아니면 P는 그대로 0.

그러니까 "상대가 4를 만들었는데 내가 안 막는 수"는 그 수를 둔 직후의 국면(상대 차례)이 펼쳐지자마자 상대 승리 증명이 돼. 그러면 다음에 나올 select_child가 그 수를 다시는 고르지 않아. 평균이 희석되던 문제가 해결되는 거야.

5.5 proven_value — 증명된 노드의 정확한 값

static double proven_value(const Node* node, int depth) {
    return mate_scaled((double)node->proven, depth + node->proof_dist);
}

루트에서 depth만큼 내려간 곳에 있는 증명된 노드의 값은 ±1을 "루트로부터 끝까지의 총 거리(depth + proof_dist)"로 메이트 스케일링한 값이야. 시뮬레이션이 증명된 노드에 도착하면 신경망을 부르지 않고 이 값을 바로 역전파해.

Solver가 하는 일 / 안 하는 일. 주석의 말: "This uses only the game rules (terminal detection), no gomoku tactics." 즉 오목 정석(열린 3, 4-3 같은)을 하드코딩한 게 아니라 "5목 = 게임 끝"이라는 규칙만으로 증명을 쌓아. 그래서 탐색이 실제로 도달한 깊이까지만 증명이 생겨. 깊은 VCF(연속 4로 이기기)를 미리 다 아는 건 아니고, 트리가 거기까지 자라야 증명돼.

6. C++ 엔진 (3) — PUCT 선택, 강제 플레이아웃, 정책 타깃 가지치기

6.1 PUCT 공식 복습

MCTS의 "선택" 단계에서 부모는 자식마다 점수를 매겨서 가장 높은 걸 골라. AlphaZero의 PUCT 점수는

score(a) = Q(a) + c_puct · P(a) · √N_parent / (1 + N(a))

  • Q(a): 지금까지 이 수를 둔 결과의 평균(부모 입장). "착취(exploitation)" 항이야.
  • U(a) = c_puct·P·√N/(1+n): 정책망이 좋다고 했는데(P 큼) 아직 덜 가 본(n 작음) 수에 주는 보너스. "탐험(exploration)" 항이야. 부모 방문 N이 커질수록 √N으로 천천히 커지고, 자식이 방문될수록 1/(1+n)으로 줄어.
  • c_puct: 둘의 균형. 이 프로젝트의 현재 값은 1.6이야(15장).

6.2 select_child — 증명된 패배 수 피하기

static int select_child(Node* node, double c_puct) {
    int best_action = -1, fallback = -1;
    double best_score = -1e18, fallback_score = -1e18;
    double sqrt_pv = std::sqrt((double)node->n_visits);
    for (auto& kv : node->children) {
        Node* ch = kv.second.get();
        double pb_c = c_puct * sqrt_pv / (1 + ch->n_visits);
        double score = -ch->mean_value + pb_c * ch->prior_prob;
        if (ch->proven == 1) {
            if (score > fallback_score) { fallback_score = score; fallback = kv.first; }
            continue;
        }
        if (score > best_score) { best_score = score; best_action = kv.first; }
    }
    return best_action >= 0 ? best_action : fallback;
}
  1. sqrt_pv: 부모 방문 수의 제곱근을 루프 밖에서 한 번만 계산해.
  2. score = -ch->mean_value + pb_c * ch->prior_prob: 위 공식 그대로야. 부호 마이너스는 4.1의 관점 규칙 때문이야.
  3. ch->proven == 1: 자식 국면에서 둘 사람(상대)이 이기는 게 증명된 수 = 내가 지는 게 확정된 수. 이런 수는 일반 후보에서 빼고 fallback에만 기록해. 증명 안 된 대안이 하나라도 있으면 절대 안 골라.
  4. 모든 수가 지는 수라면(best_action = −1) fallback 중 점수가 가장 높은 걸 돌려줘. 다만 주석대로 "Callers only select at unproven nodes" — 모든 자식이 +1이면 그 노드는 이미 −1로 증명됐을 테고, 증명된 노드에서는 선택 루프가 멈추니까(7장) 실제로 이 경로를 탈 일은 거의 없어.
  5. 동점이면 >(엄격 부등호)라서 map 순서상 먼저 나온(행동 번호가 작은) 수가 이겨.

코드에서 읽히는 세부 동작 하나. 루트를 처음 펼친 직후에는 루트의 n_visits가 0이야(펼치기만 하고 update는 안 하니까). 그러면 √0 = 0이라 U 항이 전부 0이 되고, 모든 자식의 Q도 0이라 점수가 모두 같아. 결국 첫 시뮬레이션은 행동 번호가 가장 작은 후보로 가. 루트 N이 1 이상이 되면 정상적인 PUCT가 작동하니까 영향은 미미하지만, "첫 수는 왜 저기로 갔지?"를 디버깅할 때 알아 두면 좋아. (코드 읽기로 추론한 거고 실측은 안 했어.)

6.3 counted_root_visits — "의미 있는" 방문만 세기

static long counted_root_visits(const Node& root) {
    if (!root.is_expanded || root.children.empty()) return root.n_visits;
    long n = 0;
    for (auto& kv : root.children) if (kv.second->proven != 1) n += kv.second->n_visits;
    return n;
}

시뮬레이션 예산을 "루트 자식들 중 지는 게 증명되지 않은 수들의 방문 합"으로 세. 예를 들어 트리 재사용으로 넘어온 서브트리에서, 예전엔 유망해 보였는데 나중에 패배로 증명된 수에 이미 방문 500이 쌓여 있었다면? 그 500을 예산에 넣으면 실제로 쓸모 있는 수들은 거의 탐색되지 않은 채 끝나 버려. 그래서 그런 방문은 빼고 세서, 쓸모 있는 수들에 num_simulations만큼의 방문이 채워질 때까지 계속 탐색해. 무한 루프를 막으려고 하드캡(3 × num_simulations)도 둬(7장).

6.4 강제 플레이아웃 (Forced Playouts, KataGo)

KataGo 논문(Wu 2019, 3.2절)의 기법이야. 주석의 설명:

루트 자식 c의 사전확률이 P(c)일 때, 방문 수가 n_forced(c) = √(k · P(c) · N_root)보다 적으면 그 자식을 먼저 강제로 골라. 정책망은 높게 평가하는데 첫 평가가 나빴던 수(가치망이 잘못 읽는 수비 수나 포크 칸에서 흔해)도 반박하거나 확인할 만큼은 방문을 받게 하려는 거야.

static int select_root_forced(Node* node, double c_puct, double forced_k) {
    double n_total = (double)node->n_visits;
    int best_forced = -1;
    double best_forced_score = -1e18;
    double sqrt_pv = std::sqrt(n_total);
    for (auto& kv : node->children) {
        Node* ch = kv.second.get();
        if (ch->proven == 1 || ch->prior_prob <= 0.0) continue;
        double n_forced = std::sqrt(forced_k * ch->prior_prob * n_total);
        if ((double)ch->n_visits < n_forced) {
            double score = -ch->mean_value + c_puct * sqrt_pv / (1 + ch->n_visits) * ch->prior_prob;
            if (score > best_forced_score) { best_forced_score = score; best_forced = kv.first; }
        }
    }
    return best_forced >= 0 ? best_forced : select_child(node, c_puct);
}
  • "할당량 미달" 자식이 여럿이면 그중 PUCT 점수가 가장 높은 걸 골라. 하나도 없으면 평소의 select_child로 넘어가.
  • 지는 게 증명된 수(proven == 1)와 사전확률 0인 수는 강제 대상에서 빼.
  • 루트에서만, 그리고 forced_k > 0일 때만 적용돼. 파이썬 쪽(8장)은 노이즈가 켜진 탐색(=학습 데이터를 만드는 자기대국/리그 탐색)에만 FORCED_PLAYOUT_K = 2.0을 넘기고, 평가·게이트·재라벨처럼 노이즈 없는 탐색은 0을 넘겨 평범한 PUCT를 써.

수치 감각: k=2, N=1100일 때 P=0.1인 수의 할당량은 √(2·0.1·1100) = √220 ≈ 14.8회, P=0.01인 수는 √22 ≈ 4.7회야. 정책망이 1%만 줘도 5번쯤은 들여다보게 되는 거지.

6.5 정책 타깃 가지치기 (Policy Target Pruning)

강제 방문은 탐색에는 좋지만, 그 방문 수를 그대로 학습 타깃(정책)으로 쓰면 "억지로 본 수"까지 확률을 받게 돼서 타깃이 오염돼. 그래서 반환하기 전에 강제로 준 방문을 다시 빼. 이 계산은 build_result 안에 있어.

        if (forced_k > 0.0 && kept > 0) {
            int star = -1;
            long star_n = -1;
            for (auto& kv : root.children) {
                if (kv.second->proven == 1) continue;
                if (kv.second->n_visits > star_n) { star_n = kv.second->n_visits; star = kv.first; }
            }
            double N = (double)kept;
            double sqrt_n = std::sqrt(N);
            Node* cs = root.children[star].get();
            double puct_star = -cs->mean_value + c_puct * cs->prior_prob * sqrt_n / (1.0 + cs->n_visits);
            for (auto& kv : root.children) {
                Node* ch = kv.second.get();
                if (kv.first == star || ch->proven == 1 || ch->n_visits <= 0) continue;
                long n = ch->n_visits;
                long n_forced = (long)std::floor(std::sqrt(forced_k * ch->prior_prob * N));
                double q = -ch->mean_value;
                long n_min = n;  // cannot prune if its value already beats the best child's PUCT
                if (puct_star > q) {
                    double need = c_puct * ch->prior_prob * sqrt_n / (puct_star - q) - 1.0;
                    n_min = std::max<long>(0, (long)std::ceil(need));
                }
                long pruned = std::max(n - n_forced, n_min);
                if (pruned > n) pruned = n;
                if (pruned <= 1) pruned = 0;
                shown[kv.first] = pruned;
            }
        }

단계별로 보자.

  1. star: 증명된 패배 수를 뺀 자식 중 방문이 가장 많은 수. 이 수는 절대 깎지 않아.
  2. puct_star: star의 현재 PUCT 점수.
  3. 나머지 자식 c마다 "방문을 몇 개까지 줄여도 여전히 star보다 덜 매력적인가"를 계산해. 방문이 n'일 때 c의 PUCT는 q + c_puct·P·√N/(1+n')이야. 이게 puct_star 이하가 되려면
    1 + n' ≥ c_puct·P·√N / (puct_star − q), 즉 n' ≥ need. 이 최소값이 n_min이야.
  4. q가 이미 puct_star 이상이면(가치 자체가 star의 PUCT보다 높으면) 깎을 수 없으니 n_min = n.
  5. 강제 몫만큼 빼되(n − n_forced), 위 하한(n_min)보다 작아지지는 않게: pruned = max(n − n_forced, n_min).
  6. 남은 방문이 1 이하면 0으로 만들어서 타깃에서 아예 지워. 방문 1번짜리는 그냥 노이즈니까.

숫자 예

c_puct=1.6, k=2, kept N=1000(√N≈31.62)이라 하자.

nPq(루트 관점)
star6000.50.20
c1000.20.10
  • puct_star = 0.20 + 1.6·0.5·31.62/601 ≈ 0.20 + 0.042 = 0.242
  • n_forced(c) = floor(√(2·0.2·1000)) = floor(20) = 20
  • need = 1.6·0.2·31.62/(0.242−0.10) − 1 ≈ 10.12/0.142 − 1 ≈ 70.2 → n_min = 71

결과적으로 c의 타깃 방문은 100 → 80으로 줄고, star의 비중이 커져. 강제 방문 20은 "c가 정말 나쁜지 확인하는 데" 쓰였고, 확인 결과 c가 star보다 못하니 그 몫은 타깃에서 지운 거야.

반대로 게이트·리그처럼 두 객체가 번갈아 두는 대국에서는, 엔진 A 입장에서 자기가 마지막으로 본 판과 비교하면 자기 수 + 상대 수로 두 칸이 달라. 그래서 항상 새 루트로 시작하고, 두 엔진이 트리를 공유하지 않아. 주석이 "gate/league/vs-det matches ... are completely unaffected"라고 강조하는 이유야.

  • std::move(it->second): 자식의 소유권을 부모의 map에서 꺼내 와. 그다음 root_ = std::move(promoted)를 하면 옛 루트(와 승격 안 된 나머지 형제 서브트리 전부)는 unique_ptr 소멸로 자동 해제돼.
  • promoted->parent = nullptr: 이게 빠지면 역전파가 해제된 옛 루트 메모리로 올라가서 프로그램이 죽어(use-after-free). 주석이 이걸 명시해.
  • 디리클레 노이즈가 두 번 섞이지 않는다: 노이즈는 "현재 루트의 직계 자식들"에게만, 탐색 호출마다 한 번 섞여. 승격된 노드는 부모 map에서 빠져나왔으니 다시 승격될 수 없어. 그러니 같은 노드의 사전확률에 노이즈가 두 번 섞일 수는 없다는 게 주석의 논증이야. (단, 재사용된 새 루트의 자식들은 이전 탐색에서는 루트의 손자였으니 노이즈가 섞인 적이 없어. 새 루트의 자식이 되면서 처음 섞여.)

(d) GIL 해제

GIL(Global Interpreter Lock)이란? CPython 인터프리터에는 "한 번에 한 스레드만 파이썬 코드를 실행할 수 있다"는 전역 잠금이 있어. 파이썬 스레드 여러 개를 띄워도 파이썬 코드는 사실상 하나씩 번갈아 돌아. 그런데 C++ 확장은 파이썬 객체를 안 건드리는 동안 GIL을 풀어 줄 수 있어. 그러면 그 시간에 다른 파이썬 스레드가 돌 수 있지.

        py::gil_scoped_release release;

        if (!root.is_expanded) {

        ... (노이즈, 시뮬레이션 루프 전체) ...

    return build_result(root, NUM_CELLS, BOARD_SIZE, c_puct, forced_k);

탐색 루프 전체를 gil_scoped_release 블록으로 감싸서 GIL을 풀어. 순수 C++ 트리 작업(선택, 승리 판정, 역전파) 동안 다른 스레드(예: 스레드 기반 대국의 다른 게임들, PooledEvaluator의 배치 스레드)가 돌 수 있어. 신경망 콜백을 부를 때만 gil_scoped_acquire로 잠깐 다시 잡아. 블록이 끝나면(중괄호를 벗어나면) 자동으로 GIL을 다시 잡고, 그 상태에서 build_result가 파이썬 객체를 만들어. 이 "범위 기반 잠금(RAII)"이 C++의 관용 패턴이야.

가치망(L) = +0.4   ← "X 입장에서 +0.4"
sim_player = X(1)

R: player_turn=X == sim_player → update(+0.4)   R.Q = +0.4 (X 관점)

R에서 a를 고를 때 점수 = -A.Q + U = +0.4 + U   ← X에게 좋은 수로 보임 ✓

7.4 search_batched — 가상 손실로 16개씩 모아 평가

신경망 한 번 호출에는 고정 비용(파이썬 왕복, GPU 커널 실행, 동기화)이 커. 판 1개씩 16번 부르는 것보다 16개를 한 번에 부르는 게 훨씬 빨라. 그런데 MCTS는 본질적으로 순차적이야. 다음 시뮬레이션의 경로는 이전 결과에 달려 있거든. 그래서 쓰는 표준 기법이 가상 손실(virtual loss)이야. "결과가 아직 안 나온 경로를 일단 나쁜 결과로 가정"해서, 같은 배치 안의 다음 선택이 다른 경로로 가게 만드는 거지.

가상 손실 부호 버그 (2026-09-25 발견). 코드 주석을 그대로 해석하면 이래:

"노드의 mean_value는 그 노드에서 둘 사람 관점이고, 부모는 -child->mean_value로 고른다. 그러니 가상 손실로 그 자식을 덜 매력적으로 만들려면 mean_value를 올려야(+VIRTUAL_LOSS) 한다. 이전 빌드는 전부 −VIRTUAL_LOSS를 썼고, 그게 부모를 같은 잎으로 다시 끌어당겼다. 배치 안의 16개 선택이 전부 한 잎에 몰려서, 1100 시뮬레이션이 배치 16에서는 고유 평가 ~69개에 불과했다. 꼭 막아야 하는 국면에서 배치 1은 막는 수에 방문 72%를 줬는데, 배치 16은 1.5%를 줬다."

        if (it == root_->children.end() || !it->second) return out;
        Node* n = it->second.get();
        out.append(py::make_tuple(first_action, n->n_visits));
        for (int d = 1; d < max_len && n->is_expanded && !n->children.empty(); d++) {
            int best = -1;
            long bv = 0;
            for (auto& kv : n->children) {
                if (kv.second->n_visits > bv) { bv = kv.second->n_visits; best = kv.first; }
            }
            if (best < 0) break;
            out.append(py::make_tuple(best, bv));
            n = n->children[best].get();
        }
        return out;
    }

def _board_to_input_array_batch_from_numeric(boards_list, players_list):
    n = len(boards_list)
    arr = np.stack([np.asarray(b) for b in boards_list])
    curr_vals = np.array([1 if p == 'X' else 2 for p in players_list]).reshape(n, 1, 1)
    opp_vals = np.array([2 if p == 'X' else 1 for p in players_list]).reshape(n, 1, 1)
    curr_planes = (arr == curr_vals).astype(np.float32)
    opp_planes = (arr == opp_vals).astype(np.float32)

        fork_opp = _fork_mask(opp_planes[i], empty_planes[i])
        out.append(np.stack([curr_planes[i], opp_planes[i], empty_planes[i], fork_self, fork_opp]))

동작 모델: 대국을 두는 스레드는 submit으로 요청을 큐에 넣고 event.wait()로 잠들어. 전용 배경 스레드 하나가 모든 신경망 호출을 담당해.

    def _run(self):
        pending = []
        pending_count = 0
        while True:
            timeout = self.max_wait if pending else None
            try:
                item = self._queue.get(timeout=timeout)
            except queue.Empty:
                item = 'FLUSH'
            if item is None:
                if pending:
                    self._flush(pending)
                break
            if self._stop and item == 'FLUSH':
                break
            if item != 'FLUSH':
                pending.append(item)
                pending_count += len(item['inputs'])
            if pending and (pending_count >= self.target_batch or item == 'FLUSH'):
                self._flush(pending)
                pending = []
                pending_count = 0
  • 대기 중인 요청이 없으면 무한정 기다리고(timeout=None), 있으면 max_wait초만 기다려.
  • max_wait 안에 새 요청이 안 오면 queue.Empty → 'FLUSH' → 모인 것만이라도 처리해.
  • 모인 판 수가 target_batch 이상이면 바로 처리해.
  • None은 종료 신호야.

"침묵 간격(debounce)" vs "마감 시간(deadline)". make_lrfix의 주석이 지적하듯, 여기서 max_wait는 "첫 요청 이후 최대 대기"가 아니라 "마지막 도착 이후 조용한 시간"이야. 요청이 띄엄띄엄 계속 오면 계속 기다려. 2026-09-15 측정에서는 옛 설정(48, 0.005초)으로 30만 번 넘는 flush 동안 목표 배치를 0% 달성했고 평균 배치가 ~4였어. 그래서 학습 루프는 target_batch=24, max_wait=0.05로 생성해(14장).

docstring의 설명을 정리하면 이래. 예전에는 한 에폭이 세 단계를 차례로 돌았어: 자기대국(멀티프로세스) → vs-Det(스레드) → vs-League(스레드). 각 단계는 가장 느린 게임이 끝나야 끝나니까, 단계마다 꼬리 부분에서 워커 대부분이 놀았어. 특히 리그 2게임 단계에서는 10개 워커 중 8개와 GPU 대부분이 그 단계 내내 쉬었어(평균 배치 30 → 22, 목표 달성률 57%로 하락). 그래서 2026-09-26에 한 에폭의 모든 대국을 하나의 작업 큐에 넣고 10개 워커 프로세스가 끌어가게 바꿨어.

class _TaggedPipeEvalProxy:

    def __init__(self, conn, tag):

        self.tag = tag

    def submit(self, input_arrays):
        n = len(input_arrays)
        if n == 0:
            return np.zeros((0, NUM_CELLS), dtype=np.float64), np.zeros((0,), dtype=np.float64)
        self.conn.send((self.tag, np.stack(input_arrays)))
        probs, values = self.conn.recv()

덕 타이핑(duck typing)의 좋은 예야. PooledEvaluator와 똑같은 submit(input_arrays) 메서드를 가졌으니까, MCTS 클래스는 이게 같은 프로세스의 스레드인지 다른 프로세스로 가는 파이프인지 몰라도 돼. 보내는 건 (태그, (n,5,11,11) 배열), 받는 건 (확률, 가치)야. 워커는 한 번에 대국 하나만 두고 submit마다 응답을 기다리니까, 같은 파이프에서 여러 태그의 요청이 섞일 일이 없어(docstring).

학습 샘플이 실제로 만들어지는 곳이라 한 줄씩 보자.

  1. outcome은 X 관점 결과(+1 X승, −1 O승, 0 무승부)야. 수를 둔 사람이 O면 부호를 뒤집어서 그 수를 둔 사람 관점의 z를 만들어.
  2. mix(z, q, q_weight) = mixed_value_target: z와 탐색 루트 값 q를 섞어. 현재 q_weight=0.5라서 가치 타깃 = 0.5·z + 0.5·q야(10장).
  3. mover_won이면 가중치 1.15. 이긴 쪽의 수를 조금 더 강조해.
  4. survival: 게임 총 길이 − 이 수의 번호 = 남은 수. 40에서 자르고 40으로 나눠. 길이 상한(max_plies)에 걸려 무승부 처리된 게임은 진짜 남은 길이를 모르니까 None이야.
  5. augment_sample: 8가지 대칭(회전 4 × 뒤집기 2)으로 늘려. 그래서 기록된 수 하나 = 샘플 8개야. 모든 샘플은 5-튜플 (입력, 정책, 가치, 가중치, 생존)이야.

리그 집계(_aggregate_league)는 생존 라벨 없이 4-튜플을 만들고 가중치는 1.25야. 리그 상대 쪽 수는 q가 None이라서(다른 네트워크의 값이니까) 순수 z를 써.

10.2 sims_for_state — 국면별 시뮬레이션 수

def sims_for_state(num_empty, base_sims, boosted_sims=None, boost_threshold=0, boost_when_narrow=False):
    if not boosted_sims:
        return base_sims
    if boost_when_narrow:
        sims = boosted_sims if num_empty <= boost_threshold else base_sims
    else:
        sims = boosted_sims if num_empty > boost_threshold else base_sims
    if num_empty > NUM_CELLS - 10:
        sims = max(sims, boosted_sims)
    return sims

10.3 mixed_value_target — z/q 혼합

def mixed_value_target(z, q, q_weight):
    if q is None or q_weight <= 0.0:
        return z
    return (1.0 - q_weight) * z + q_weight * float(q)

가치 타깃을 정하는 핵심 식이야.

  • z: 실제 게임 결과(그 수를 둔 사람 관점, +1/0/−1). 정직하지만 노이즈가 커. 게임 하나에 정보가 1비트뿐이고, 좋은 수를 둬도 나중의 실수로 지면 −1이 되니까.
  • q: 그 수를 정한 탐색의 루트 값. 탐색의 수읽기가 담겨 있어서 분산이 작지만, 가치망 자체의 편향을 물려받을 수 있어.
  • 현재 q_weight = 0.5 → 타깃 = (z + q) / 2. docstring의 근거: 자유룰에서 수비 쪽은 개별 수의 품질과 상관없이 대개 지니까, z만 쓰면 가치망이 "수비 = 패배"를 계속 다시 배웠어. ep435의 비관성 측정에서 가치망 원시 출력 −0.42 vs 실제 결과 −0.09였고, 그때 탐색 값은 이미 −0.14로 실제에 가까웠어. Oracle의 "Lessons from AlphaZero" 4편과 Lc0의 q_ratio를 참고했어.
  • q가 None(리그 상대 쪽 수: 다른 네트워크의 값이라 의미가 다름)이면 순수 z.

10.4 annealed_value — 탐험 노이즈 담금질

def annealed_value(epoch, anneal_epochs, start_value, end_value):
    if anneal_epochs <= 0:
        return start_value
    t = min(1.0, epoch / anneal_epochs)
    return start_value + (end_value - start_value) * t

에폭에 따라 start에서 end로 직선으로 줄이고, 그 뒤로는 end를 유지해. 현재 설정: noise_weight 0.25 → 0.10, dirichlet_alpha 0.3 → 0.15, 기간 150에폭. 누적 에폭이 이미 800을 넘었으니(train_state: 804) 지금은 항상 end 값(0.10, 0.15)이야. 학습 루프에는 정책 엔트로피가 0.5 아래로 떨어지면 담금질을 멈추는 안전밸브도 있어(14장).

10.7 _canonical_symmetry_openings — 대칭 대표 칸

def _canonical_symmetry_openings(board_size):
    def symmetries(r, c, n):
        yield (r, c)
        yield (c, n - 1 - r)
        yield (n - 1 - r, n - 1 - c)
        yield (n - 1 - c, r)
        yield (r, n - 1 - c)
        yield (n - 1 - r, c)
        yield (c, r)
        yield (n - 1 - c, n - 1 - r)

    seen = set()
    reps = []
    for r in range(board_size):
        for c in range(board_size):
            if (r, c) in seen:
                continue
            orbit = set(symmetries(r, c, board_size))
            seen |= orbit
            reps.append((r, c))
    return reps

정사각형 판의 대칭(회전 4 × 뒤집기 2 = 8개, "이면체군 D4")으로 같아지는 칸들을 하나의 궤도(orbit)로 묶고, 궤도마다 대표 하나를 뽑아. 빈 판의 첫 수는 대칭으로 같은 칸이면 본질적으로 같은 게임이니까, 대표만 시도하면 중복이 없어.

11×11(홀수)에서 대표 칸 개수는 판의 1/8 삼각형(대각선 포함)에 해당해. 한 변의 절반이 6칸(0~5)이니 6×7/2 = 21개야(행 0~5에서 c ≥ r인 칸, 즉 6+5+4+3+2+1). 주석의 "42-game (21 openings x 2 sides)"와 맞아.

평가용 _ALL_CELLS는 121칸 전부를 시드 1109로 섞은 거고, 게이트용 _GATE_OPENING_SQUARES는 21개를 시드 910으로 섞은 뒤 앞의 10개만 써. 시드를 고정하니까 재실행해도 같은 칸이 나와.

11.1 왜 게이트가 필요한가

주석의 요지: 경사하강법으로 계속 갱신되는 정책은 단조롭게 강해진다는 보장이 없어. 이 프로젝트에서도 "500에폭 전 체크포인트는 이기는데 100에폭 전 것에는 지는" 비추이적(non-transitive) 강도가 측정됐어. AlphaGo Zero의 해법은 검증되지 않은 가중치를 새 기준으로 삼지 않는 것이야. 후보가 현재 best를 공정한 대국에서 이겨야만 승격돼. 이 프로젝트의 구조는 이래:

객체역할
model매 optimizer.step으로 바뀌는 학습 중 가중치. 디스크: alphazero_mcts_11x11.pth(매 에폭 저장)
gen_model데이터 생성 전용 모델. 항상 best와 같은 가중치. 절대 학습 안 함
best 체크포인트best_mcts_11x11.pth. 게이트 통과 시에만 갱신

즉 자기대국 데이터는 항상 "검증된" 모델이 만들고, 학습은 계속 model을 고치고, 주기적으로 model이 best를 이기면 best와 gen_model을 model로 교체해.

12.3 리그 대국 _play_one_mcts_vs_league_game의 핵심

  • 리그 쪽 수는 q 자리에 None을 넣어(순수 z). 다른 네트워크의 값이니까.
  • 2026-09-28부터 리그 쪽에도 PCR이 적용돼(같은 확률). 길이 상한 max_plies(90)은 판 위의 돌 수로 셈해.
  • X의 첫 수를 오프닝 칸에 강제로 둬. 리그 쪽이 탐욕적이라, 리그가 선수일 때 같은 오프닝이 반복되는 걸 막으려는 거야.

def _acquire_single_instance_lock():
    if os.path.exists(LOCK_PATH):
        try:
            with open(LOCK_PATH) as f:
                existing_pid = int(f.read().strip())
        except (ValueError, OSError):

작은 허점. Windows는 PID를 재사용하니까, 죽은 트레이너의 PID를 우연히 다른 프로세스가 받으면 "살아 있음"으로 오판해서 학습이 시작되지 않을 수 있어. 드물지만 "학습이 안 켜지는데 로그에 'Another trainer is already running'이 찍힌다"면 이걸 의심해 봐. (코드 읽기로 추론한 가능성이고, 실제로 일어난 적이 있는지는 확인 안 했어.)

16. 한 수가 두어지기까지: 전체 호출 흐름 다시 보기

지금까지 본 걸 "자기대국에서 수 하나"의 관점으로 이어 붙이면 이래.

[메인 프로세스] generate_epoch_games_unified
   └ task_queue.put(("self3", "self", (None,None), selfplay_cfg))
[워커 프로세스 k] _worker_main → _run_task("self") → prod._play_one_mcts_game(None, None, 1100, ...)
   └ MCTS(c_puct=1.6, eval_batch_size=16, shared_cache=워커의 gen 캐시, pooled_evaluator=gen 프록시)
   └ (수마다) PCR 동전 던지기 → full: sims = 2200(돌<10) 또는 1100, 노이즈 켬
        └ MCTS.search → _search_cpp → forced_k = 2.0
             └ [C++] MCTSEngine.search_batched
                  ├ prepare_root: 직전 수의 자식을 루트로 승격 (트리 재사용)
                  ├ GIL 해제
                  ├ 루트 노이즈 (0.9·P + 0.1·Dir(0.15))
                  └ 반복: 16개 경로 선택(가상 손실 +1) → 끝난 판/증명 판정
                          → 중복 제거 → GIL 획득 → eval_batch_fn(판 리스트)
                               └ [파이썬] 캐시 확인 → 입력 평면 5장(포크 마스크 C++)
                                  → 프록시.submit → 파이프 → [메인] 코디네이터
                                       → 24판 모이면 gen_model forward (GPU, GTX 1050)
                                  ← (확률 121, 가치) ← 파이프
                          → 펼치기(반경 2 후보, 즉시 승리 증명) → 역전파(부호 교대)
                  └ build_result: 증명 반영, 정책 타깃 가지치기, 루트 값 재계산

   └ 게임 끝 → (history, outcome, ply_indices, total_plies)
[메인] result_queue → _aggregate_selfplay: z/q 혼합, 가중치, 생존, 8대칭
   → replay_buffer.extend → 학습 스텝

이 흐름에서 꼭 기억할 다섯 가지.

  1. 가치는 항상 "그 노드에서 둘 사람" 관점이고, 부모는 -Q로 고른다. 가상 손실 버그가 바로 이 규칙을 어긴 거였다.
  2. 학습 데이터의 정책 타깃은 "날 방문 수"가 아니라 증명·강제 플레이아웃 가지치기가 반영된 방문 수다.
  3. 가치 타깃은 0.5·z + 0.5·q이고, 라벨 없는 샘플은 NaN으로 마스크된다.
  4. 데이터는 항상 gen_model(=best)이 만들고, 학습은 model을 바꾸고, 게이트가 둘을 잇는다.
  5. 모든 위험한 최적화(통합 풀, C++ 엔진, fork_mask_cpp)에는 옛 경로로의 폴백이 있다. 그 대신 폴백 경로는 기능이 조금씩 달라(예: 파이썬 MCTS에는 Solver가 없음).
