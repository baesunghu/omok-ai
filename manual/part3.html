0. 들어가며: 왜 "공학" 편이 따로 필요한가

1부와 2부에서 AlphaZero가 무엇을 하는지(신경망이 수를 제안하고, MCTS가 그 제안을 검증하고, 그 결과로 다시 신경망을 학습시키는 순환)를 봤어. 이 3부는 어떻게 그걸 i5-8300H(4코어 8스레드)와 노트북용 GTX 1050 한 대로 46일 안에 돌렸는지를 다뤄.

AlphaZero 논문은 수천 개의 TPU로 학습했어. 우리가 가진 건 그 몇십만분의 일이야. 그래서 이 프로젝트에서 시간의 상당 부분은 "알고리즘을 바꾸는 일"이 아니라 "같은 알고리즘을 덜 낭비하면서 돌리는 일"에 들어갔어. 그리고 이 부분에서 가장 큰 교훈이 나왔어. 코드가 빨라 보인다고 해서 맞게 돌고 있다는 보장은 없다는 거야. 대표적인 예가 5절의 가상 손실 부호 버그야. 한 달 넘게 "1100번 탐색"이라고 믿었던 게 실제로는 약 69번의 평가였어.

이 부의 읽는 법. 각 절은 (1) 개념을 처음부터 설명하고, (2) 실제 코드 조각을 보여주고, (3) 대화 기록에 남은 역사(언제, 왜 바뀌었는지)를 붙이는 순서로 되어 있어. 코드는 전부 저장소에서 그대로 인용했어. 숫자 중 기록에서 직접 확인하지 못한 것은 그렇다고 표시했어.

1.2 한 수를 두는 데 드는 일

AlphaZero식 대국에서 한 수를 두려면 MCTS가 N번 시뮬레이션을 해. 각 시뮬레이션은 대략 이렇게 생겼어.

1. 선택(select): 루트에서 PUCT 점수가 가장 높은 자식을 따라 잎까지 내려간다   [CPU]
2. 평가(evaluate): 잎 국면을 신경망에 넣어 정책 p와 가치 v를 얻는다         [GPU]
3. 확장(expand): 잎에 자식 노드를 만들고 p를 사전확률로 넣는다              [CPU]
4. 역전파(backup): v를 잎에서 루트까지 부호를 바꿔가며 더한다              [CPU]

우리 설정(_restart_train.py)은 num_simulations=900이고, 웹판의 "어려움"은 1100회야. 한 판이 수십 수니까, 한 판에 신경망 평가가 수만 번 필요해. 대화 기록의 연산량 어림(18절)은 "판당 약 2.5만 번"을 썼어.

여기서 핵심 질문이 생겨. 2번(GPU)과 나머지(CPU)를 어떻게 겹쳐서 둘 다 놀지 않게 할까? 이 질문 하나가 이 부 전체의 뼈대야.

2. C++ 엔진과 pybind11

2.1 왜 Python만으로는 안 됐나

처음 MCTS는 순수 Python이었어. Python은 쓰기 쉽지만 "작은 일을 엄청 많이" 하는 데 약해. MCTS의 선택 단계는 노드마다 자식 수십 개의 PUCT 점수를 계산하고, 최댓값을 고르고, 포인터를 따라가는 일을 수백만 번 반복해. Python에서는 숫자 하나 더하는 것도 객체 생성, 타입 확인, 참조 카운트 갱신을 동반해. C++에서는 같은 일이 기계어 몇 줄이야.

2.2 pybind11이란

pybind11은 C++ 코드를 Python 모듈처럼 import 할 수 있게 해주는 헤더 라이브러리야. C++ 클래스에 몇 줄 표시만 하면, 빌드 결과물(Windows에서는 .pyd 파일, 사실상 DLL)을 Python이 그냥 불러와.

역할 분담은 이렇게 했어.

  • C++: 트리 노드, PUCT 선택, 승리 판정, 역전파, 캐시. 즉 "작고 많은 일" 전부.
  • Python: 신경망(PyTorch). C++이 잎 국면을 모아서 Python 함수(eval_fn 또는 eval_batch_fn)를 콜백으로 부르면, Python이 GPU에 보내고 결과를 돌려줘.

3. GIL과 그 해제

3.1 GIL이란

CPython(일반 Python)에는 GIL(Global Interpreter Lock)이라는 자물쇠가 하나 있어. "Python 객체를 건드리는 코드는 한 번에 한 스레드만 실행한다"는 규칙이야. 그래서 Python 스레드를 10개 만들어도, Python 코드 자체는 사실상 한 번에 하나씩만 돌아.

예외가 있어. C/C++ 확장 코드가 "나는 지금 Python 객체를 안 건드린다"고 선언하고 GIL을 내려놓으면, 그동안 다른 스레드가 Python 코드를 돌릴 수 있어. PyTorch도 GPU 연산을 기다리는 동안 GIL을 놓아.

3.2 엔진에서의 해제

{
    py::gil_scoped_release release;      // 이 블록 동안 GIL을 놓는다

    if (!root.is_expanded) {
        expand_node(&root, root_board, root_player);
    }
    ... // 노이즈, 선택, 승리 판정, 역전파 -- 전부 순수 C++
}

그리고 신경망을 불러야 하는 순간에만 다시 잡아.

probs.resize(NUM_CELLS);
py::gil_scoped_acquire acquire;          // Python 함수를 부르기 직전에만 잡는다
py::object result = eval_fn(board_to_pyarray(b), player == 1 ? std::string("X") : std::string("O"));

gil_scoped_release/acquire는 C++의 RAII(객체가 만들어질 때 자원을 잡고, 범위를 벗어날 때 자동으로 놓는 패턴)를 써. 그래서 중간에 예외가 나도 GIL 상태가 꼬이지 않아.

그런데 학습 루프는 결국 멀티"프로세스"로 갔어. GIL 해제로 스레드끼리 트리 탐색은 겹칠 수 있지만, 입력 변환·결과 처리 같은 Python 부분은 여전히 한 줄로 서야 해. 그래서 학습 자기대국은 11절의 프로세스 풀로 옮겼어. 프로세스마다 Python 인터프리터가 따로 있으니 GIL도 따로야. 반면 웹 서버(16절)는 스레드 방식이고, 거기서는 GIL 해제가 그대로 중요해.

4. 배치 평가와 가상 손실(virtual loss)

4.1 왜 배치가 필요한가

GPU는 "한 번에 하나"를 처리할 때 비효율적이야. 11x11 국면 하나를 신경망에 넣는 것과 16개를 넣는 것은 시간이 거의 비슷해. 커널을 띄우는 고정 비용과 CPU↔GPU 복사 비용이 대부분이기 때문이야. 그래서 잎 16개를 모아 한 번에 평가하면 GPU 호출 횟수가 16분의 1로 줄어.

4.2 문제: 16개를 어떻게 다르게 고르나

MCTS는 본래 순차적이야. 1번 시뮬레이션 결과가 역전파된 뒤에야 2번 시뮬레이션이 "어디로 갈지"가 바뀌어. 그런데 배치로 모으려면 1번의 평가 결과가 나오기 전에 2~16번을 골라야 해. 아무 조치 없이 고르면 16개가 전부 같은 잎으로 가. 트리가 아직 안 바뀌었으니까.

4.3 가상 손실의 아이디어

"이 경로는 지금 누가 평가 대기 중이야"라는 표시로, 그 경로의 노드를 일시적으로 나쁘게 보이게 만드는 거야. 방문 수를 1 올리고 가치를 "졌다" 쪽으로 미리 더해두면, 다음 선택은 다른 곳을 고르게 돼. 평가가 끝나면 이 가짜 값을 빼고 진짜 값을 넣어.

선택 단계 (그룹의 각 시뮬레이션마다):
    경로의 각 노드: n_visits += 1, total_value += (가상 손실)   ← 임시 표시
그룹 16개 선택 완료 후:
    경로의 각 노드: n_visits -= 1, total_value -= (가상 손실)   ← 표시 제거
신경망 한 번 호출로 16개 평가 → 진짜 역전파

4.4 그룹 단위 루프

long hard_cap = 3L * std::max(1, num_simulations);
long spent = 0;
while (spent < hard_cap) {
    if (root.proven != 0) break;  // result already proven: nothing left to search
    long remaining = (long)num_simulations - counted_root_visits(root);
    if (remaining <= 0) break;
    int group_size = (int)std::min<long>(eval_batch_size, remaining);
    spent += group_size;
    ...

운영에서는 eval_batch_size=16이야. 웹 서버에서도 search_batched(..., N, WIN_LENGTH, 16, 0.0)로 16을 넘겨. hard_cap은 Solver(9절)가 증명된 자식의 방문을 "세지 않는" 규칙과 맞물려 루프가 영원히 돌지 않게 하는 안전장치야.

그룹 안에서 같은 국면이 두 번 나오면 한 번만 평가해. key_to_idx로 중복을 걸러내고, 이미 캐시에 있으면 아예 건너뛰어(6절).

5. 가상 손실 부호 버그: 1100번이 69번이던 사건

5.1 관점(perspective) 규약 복습

우리 엔진에서 노드의 mean_value는 그 노드에서 둘 차례인 사람의 관점이야. 부모는 자식을 고를 때 -child->mean_value를 써. 자식 국면에서 상대가 좋으면(값이 크면) 부모에게는 나쁘니까 부호를 뒤집는 거야.

static double puct_score(double c_puct, double sqrt_pv, Node* child) {
    double pb_c = c_puct * sqrt_pv / (1 + child->n_visits);
    return -child->mean_value + pb_c * child->prior_prob;
}

5.2 무엇이 틀렸나

가상 손실은 "부모가 이 자식을 덜 고르게" 만들어야 해. 부모는 -mean_value를 보니까, 자식의 mean_value를 올려야 부모 눈에 나빠 보여. 그런데 그 전의 모든 빌드는 빼고 있었어. 결과적으로 가상 손실이 "가상 이득"이 되어, 방금 고른 잎이 더 매력적으로 보였고, 16개 선택이 전부 같은 잎으로 몰렸어.

// Virtual loss must make this node LESS attractive to
// its parent. A node's mean_value is from ITS OWN
// mover's perspective and the parent selects on
// -child->mean_value, so the pending visit has to push
// mean_value UP (+VIRTUAL_LOSS). Every earlier build
// used -VIRTUAL_LOSS, which pulled the parent back to
// the same leaf: all eval_batch_size selections in a
// batch landed on one leaf, so 1100 sims at batch 16
// were only ~69 distinct evaluations (found 2026-09-25:
// on a must-block position batch 1 put 72% of visits on
// the block, batch 16 put 1.5%).
node->total_value += VIRTUAL_LOSS;
node->mean_value = node->total_value / node->n_visits;

숫자로 따져보자. 1100 ÷ 16 ≈ 68.75야. 그룹 하나가 사실상 평가 1번이었으니 서로 다른 평가는 약 69번이었던 거야. 방문 수는 1100이 찍히지만, 그 방문은 16개씩 뭉쳐 있었어.

5.3 어떻게 찾았나 (2026-09-25)

  1. 그 전부터 이상한 현상이 있었어. 기록(2026-09-24경)에는 "PUCT/배치 탐색 구조가 강한 prior 하나에 방문을 몰아주지 못하고 분산시키는 특성일 수 있음"이라는 가설이 남아 있어.
  2. 방어 업그레이드 작업 중 "반드시 막아야 하는" T자 국면을 조사하다가, 배치 크기를 1로 바꿔서 16일 때와 분포가 달라지는지 시험했어. 원리적으로 가상 손실이 맞다면 배치 크기는 결과를 크게 바꾸면 안 돼.
  3. 결과: 배치 1에서는 막는 수에 방문의 72%, 배치 16에서는 1.5%. 버그 확정.
  4. 수정 후 방문이 "16 단위로 뭉치지 않고 제대로 퍼져(192, 158, 126…)" 나오는 것을 확인.

당시 정리표에는 "가상 손실 부호 버그 수정 | 완료, 검증 통과. 탐색 효율 약 16배 차이"라고 적혀 있어. 그리고 배포 순서를 정할 때, 효과가 너무 커서 다른 변경(메이트 거리, V3 남은 수 헤드)과 섞으면 기여도를 구분할 수 없으니 버그 수정만 먼저 배포하는 쪽을 택했어.

교훈. 이 버그는 코드가 "느리게" 돌지도, 오류를 내지도 않았어. 오히려 GPU 호출이 적어서 빨랐어. 증상은 오직 "실력이 기대보다 안 오름"이었고, 그건 다른 원인(데이터, 학습률, 가치망)으로도 설명될 수 있었어. 이런 버그를 잡는 방법은 같아야 할 두 설정(배치 1과 16)을 나란히 돌려 비교하는 불변식(invariant) 검사야. 또 그 이전의 Rapfi 측정들도 이 버그가 있는 엔진으로 잰 것이라, 모델 간 상대 비교는 유효하지만 절대 실력은 과소평가되었을 거라는 단서가 기록에 남아 있어.

6. 평가 캐시와 후보 칸 줄이기

6.1 평가 캐시

한 번의 탐색 안에서 같은 국면이 다른 수순으로 다시 나오는 일은 흔해(오목은 두는 순서만 다르고 결과 국면이 같은 경우가 많아). 그래서 엔진은 국면을 문자열 키로 만들어 결과를 기억해.

auto cache_key = [&](const std::vector<int8_t>& b, int player) {
    std::string s;
    s.reserve(NUM_CELLS + 1);
    for (auto v : b) s.push_back('0' + v);
    s.push_back('0' + player);
    return s;
};

칸 121개를 '0','1','2'로 적고 마지막에 둘 차례를 붙인 122글자 키야. 이 캐시는 search 호출마다 새로 만들어지는 지역 변수야. 신경망이 학습으로 바뀌면 옛 평가는 틀린 값이 되니까 오래 들고 있지 않는 거야. 통합 풀(11절)의 워커들도 "프로세스별 캐시를 매 호출(=에폭)마다 초기화"한다고 주석에 적혀 있어.

6.2 후보 칸: 반경 안의 빈칸만

11x11은 빈칸이 최대 121개야. 하지만 돌에서 멀리 떨어진 칸은 거의 의미가 없어. 엔진은 기존 돌로부터 NEIGHBOR_RADIUS 안의 빈칸만 자식으로 만들어(relevant_cells). 판이 비어 있으면 모든 빈칸을 써.

2026-09-10 개입 기록에는 "250 시뮬레이션에서 반경 2 후보 약 45개면 자식당 방문이 약 5번"이라는 측정이 있어. 이게 시뮬레이션 수를 900으로 올린 이유였어(그때는 가상 손실 버그 때문에 실제 평가가 이보다도 훨씬 적었다는 걸 아직 몰랐지만).

7. 트리 재사용과 같은 국면 재사용

7.1 아이디어

내가 수 A를 두기 위해 탐색하면, 트리 안에는 "A를 둔 뒤 상대가 B를 두면…" 같은 하위 트리가 이미 자라 있어. 자기대국에서는 같은 엔진이 다음 수도 두니까, 실제 둔 수의 자식을 새 루트로 "승격"하면 그 아래 방문을 공짜로 이어받을 수 있어.

7.2 규칙 (prepare_root)

if (diff_count == 1 &&
    root_board_[diff_idx] == 0 &&
    new_board[diff_idx] == root_player_) {
    auto it = root_->children.find(diff_idx);
    if (it != root_->children.end() && it->second) {
        std::unique_ptr<Node> promoted = std::move(it->second);
        promoted->parent = nullptr;
        root_ = std::move(promoted);
        ...
        return true;
    }
}

조건을 풀면 이래.

  • 이전 루트 국면과 정확히 한 칸만 다르고,
  • 그 칸이 비어 있다가 이전 루트에서 둘 차례였던 사람의 돌로 채워졌고,
  • 이전 루트에 그 칸의 자식이 있으면 → 그 자식을 이동(move, 복사 아님)시켜 새 루트로. parent=nullptr로 끊어서 역전파가 이미 해제된 옛 부모로 넘어가지 않게 해.

그 외 모든 경우(첫 호출, 두 칸 이상 차이, 자식 없음)는 새 트리로 시작해. 게이트·리그 대국처럼 서로 다른 엔진 둘이 번갈아 두면 각 엔진 입장에서 국면이 두 칸씩 달라지니 항상 새로 시작해. 주석에 "gate/league/vs-det matches ... are completely unaffected"라고 명시돼 있어.

잠깐, 자기대국에서는 한 칸 차이가 맞나? 자기대국은 한 엔진 인스턴스가 흑백을 다 두니까, 매 수마다 직전 루트에서 한 수 둔 국면이 들어와. 그래서 "한 칸 차이, 직전 차례 사람의 돌" 조건이 성립해. 그리고 노이즈는 현재 루트의 직계 자식에만, 호출당 한 번 들어가. 한 노드가 루트로 승격되는 건 일생에 한 번뿐이라(승격되면 부모의 자식 목록에서 빠지므로) 같은 노드에 노이즈가 두 번 섞이는 일은 없어.

7.3 같은 국면 재사용 (2026-09-28)

// Same position, same mover (2026-09-28): keep the tree, so a caller
// can run one search in chunks (the analysis board streams every 50
// sims). Training never re-searches an identical position.
if (diff_count == 0 && new_player == root_player_) {
    return true;
}

이건 웹판을 위해 넣은 규칙이야. 국면이 완전히 같으면 트리를 그대로 두고 이어서 탐색해. 그러면 1100번 탐색을 "16번, 32번, 48번 …"처럼 조각내서 부르면서 중간 결과를 화면에 보낼 수 있어. 주석에는 50이라고 적혀 있지만, 실제 server.py는 CHUNK = 16(엔진 배치 크기와 같음)을 써. 처음 50으로 만들었다가 16으로 바꾼 것으로 보여(주석이 갱신되지 않음).

7.4 예산이 "새 방문"이 아니라 "총 방문"이라는 점

num_simulations는 "이번 호출에서 새로 할 횟수"가 아니라 "루트가 도달해야 할 방문 수"야(counted_root_visits(root) >= num_simulations이면 종료). 그래서 재사용된 트리가 이미 400번 방문을 갖고 있으면 이번 호출은 나머지만 채워. 이게 다음 절 PCR 계산이 틀린 이유와 직결돼.

8. PCR: 빠른 탐색과 정밀 탐색 섞기, 그리고 틀렸던 계산

8.1 PCR이란

Playout Cap Randomization(KataGo, Wu 2019). 자기대국의 각 수마다 동전을 던져서,

  • 확률 full_search_prob로 정밀 탐색(우리는 900회) → 이 수는 정책 학습 데이터로 기록,
  • 나머지는 빠른 탐색(fast_sims=150) → 게임을 진행시키기만 하고 정책 데이터로는 안 씀.

게임 결과(가치 목표)는 모든 수에 쓸 수 있으니, 같은 계산으로 더 많은 판을 끝내서 가치망 데이터를 늘리는 게 목적이야. 현재 설정은 full_search_prob=0.5, fast_sims=150, full_search_prob_other=0.5(리그 대국에도 적용)야.

8.2 처음의 계산과 그 오류 (2026-09-26)

처음 계산은 단순했어. "전체 수의 1/3만 900회, 나머지 150회면 수당 평균 비용이 크게 줄어드니 같은 시간에 2~3배 많은 판"이라는 식이었어. 배포 전 다관점 검토와 시뮬레이션에서 이게 틀렸다는 게 드러났어.

상황이번 호출에서 실제로 새로 하는 시뮬레이션
정밀 → 정밀 (PCR 없음)직전 탐색의 하위 트리를 물려받아서, 1100회 기준 약 440회만 새 작업(기록의 수치)
빠른 → 정밀직전 빠른 탐색이 150회라 물려받을 하위 트리가 작음 → 거의 1000회 가까이 새로

즉 PCR이 없을 때 이미 트리 재사용이 "공짜 할인"을 주고 있었는데, PCR은 그 할인을 깨뜨려. 기록의 결론은 "같은 양의 학습 데이터가 1.4~1.7배의 계산을 먹는다. 얻는 건 속도가 아니라 판 수다"였어.

조정 전: 24판, 정밀 33%  → 약 1.7배 계산
조정 후: 16판, 정밀 50% (커리큘럼 4, 오프닝 2) → 약 1.4배 계산, 판 수 2배, 학습 데이터 양 동일

실제 배포 후 관찰은 "자기대국 판 수 2배에 시간은 약 10% 증가"였어. 예상(1.4배)보다 나았던 건 11절의 통합 풀이 단계 사이 대기 시간을 없애서 PCR의 추가 비용 대부분을 상쇄했기 때문으로 해석했어.

그래서 PCR을 왜 계속 썼나. 판이 많아지면 학습 데이터 간 상관이 줄어(한 판에서 나온 수들은 서로 비슷하니까). 가치망은 판 결과로 배우니 판 수가 곧 가치망 데이터 수야. 그리고 정책망은 정밀 탐색한 수로만 배우니 질이 떨어지지 않아. "계산 절약 장치"가 아니라 "다양성 장치"로 의미를 고쳐 이해한 거야.

9. MCTS-Solver와 메이트 거리

9.1 평균의 함정

일반 MCTS는 값을 평균해. 그런데 "이 수를 두면 상대가 바로 5목을 만들 수 있다"는 수를 생각해봐. 상대의 응수가 여러 개고 그중 하나만 이기는 수라면, 평균은 -1이 아니라 -0.86쯤으로 나와. 기록(ep470 측정)에 따르면, 가치망이 막는 수까지 "막아도 진다"(-0.9)로 오판하면 탐색이 막는 수와 안 막는 수를 구분하지 못해 고정 시험 국면 20개 중 3개에서 열린 4를 방치했어.

9.2 Solver의 규칙 (Winands et al. 2008)

  • 확장할 때, 두면 5목이 되는 자식은 즉시 "증명된 승리"로 표시(mark_immediate_wins).
  • 자식 중 하나라도 (자식의 둘 사람 관점에서) 증명된 패배면 → 이 노드는 증명된 승리.
  • 모든 자식이 증명된 승리면 → 이 노드는 증명된 패배.
  • 선택 단계는 대안이 있는 한 증명된 패배 수로 들어가지 않고, 증명된 노드에 도착하면 그 정확한 값을 역전파.
  • 결과 방문 분포에서는 증명된 패배 수를 지우고, 증명된 승리 루트는 가장 빠른 승리 수만 보고.

주석에 강조된 점은 "This uses only the game rules (terminal detection), no gomoku tactics"야. 사람이 만든 오목 전술(VCF 등)이 아니라 오직 "5목이면 끝"이라는 규칙만 써. 그래서 AlphaZero의 "규칙 외 지식 없음" 원칙과 충돌하지 않아.

9.3 공학적 이득

  1. 탐색 조기 종료: if (root.proven != 0) break; 결과가 증명되면 남은 예산을 쓰지 않아. 웹 서버도 증명된 후보가 나오면 조각 탐색을 멈춰.
  2. 예산 보정: counted_root_visits는 증명된 패배 자식에 쓴 방문을 빼고 세. 트리 재사용 뒤 반박된 옛 주 수순의 방문이 예산을 갉아먹지 않게.
  3. 학습 목표 정리: 지는 수에 방문이 남아 정책 목표를 오염시키지 않음.

9.4 메이트 거리 (2026-09-25)

static const double MATE_DISTANCE_ALPHA = 0.005;
static const double MATE_DISTANCE_FLOOR = 0.5;

static double mate_scaled(double v, int depth) {
    double mag = 1.0 - MATE_DISTANCE_ALPHA * depth;
    if (mag < MATE_DISTANCE_FLOOR) mag = MATE_DISTANCE_FLOOR;
    return v * mag;
}

11x11 자유 규칙 오목은 흑이 거의 다 이기니까, 백 입장에서는 대부분 수순이 -1로 끝나서 "더 오래 버티는 수"를 고를 이유가 없었어. 깊이당 0.005씩 크기를 줄이면(최소 0.5) 늦게 지는 게 조금 덜 나쁘고, 빨리 이기는 게 조금 더 좋아져. 체스 엔진의 "mate in N"과 같은 발상이야. 트리 재사용 뒤에는 재사용된 하위 트리 값이 옛 루트 기준(1~2수 깊이 차이)으로 스케일되어 있다는 작은 오차를 "단순함을 위해 수용"한다고 주석에 적혀 있어.

10. 강제 탐색(forced playouts)과 정책 목표 가지치기

10.1 문제

신경망이 높게 평가한 수인데 첫 평가가 나쁘게 나오면(방어 수나 쌍삼 자리를 가치망이 오판하는 전형적 경우), PUCT는 그 수를 금방 버려. 그러면 그 수가 정말 나쁜지 확인할 기회가 없어.

10.2 해법 (KataGo Sec. 3.2, 2026-09-27)

루트에서만, 사전확률 P(c)인 자식 c가 다음보다 방문이 적으면 먼저 고른다.

n_forced(c) = sqrt(k * P(c) * N_root)

예: k=2, P=0.1, N=900이면 sqrt(2×0.1×900)=sqrt(180)≈13.4번은 보장. 학습용 노이즈 탐색에만 k=2를 넘기고, 평가·게이트·재라벨 탐색은 k=0(순수 PUCT)이야. 웹판도 search_batched(..., 16, 0.0)으로 끄고 있어.

10.3 가지치기

강제로 준 방문은 "이 수가 좋아서"가 아니라 "확인용"이니까 학습 목표에서는 빼야 해. build_result는 가장 많이 방문한 자식 c*를 빼고, 각 자식의 방문을 "그 자식의 PUCT가 c*의 PUCT를 넘지 않는 선까지" 줄이되 강제분 이상은 빼지 않고, 1 이하로 남으면 0으로 지워.

long n_forced = (long)std::floor(std::sqrt(forced_k * ch->prior_prob * N));
...
long pruned = std::max(n - n_forced, n_min);
if (pruned > n) pruned = n;
if (pruned <= 1) pruned = 0;
shown[kv.first] = pruned;

공학적으로 보면 이건 "적은 시뮬레이션 예산에서 탐색의 맹점을 줄이는 값싼 방법"이야. 시뮬레이션을 두 배로 늘리는 것보다 훨씬 싸.

11.1 이전 구조의 낭비

11.2 새 구조 (2026-09-26)

  • 한 에폭의 모든 대국(자기대국, 커리큘럼·오프닝 시작, vs-Det, vs-League)을 하나의 작업 큐에 넣고, 10개 워커가 긴 판부터 꺼내 둬. 큐가 빌 때까지 워커가 쉬지 않고 GPU는 계속 꽉 찬 배치를 받아.
  • 워커는 신경망 가중치를 갖지 않아. 평가 요청에 모델 태그를 붙여 보내면, 부모의 코디네이터가 태그별로 묶어 모델마다 한 번씩 순전파해. 그래서 리그 대국의 상대 쪽은 리그 체크포인트로, 나머지는 현재 세대 모델로 평가돼. GPU 메모리에 모델 사본이 10개 생기지 않는 것도 노트북 GPU에선 중요해.
  • 워커는 게임 로직을 새로 짜지 않고 기존 운영 함수를 그대로 불러. "손으로 옮긴 게임 로직이 조용히 어긋나는 일"을 막기 위한 원칙이야.
  • 샘플 가중치(이긴 쪽 1.15, vs-Det 1.5, vs-League 1.25)와 순서도 기존 함수와 똑같이 모아.

11.3 Windows의 spawn

Linux의 fork는 부모 메모리를 복사해서 자식을 만들지만, Windows의 spawn은 새 Python을 띄워 스크립트를 다시 import해. 그래서 _restart_train.py에는 이런 주석이 있어.

    _acquire_single_instance_lock()

이 가드가 없을 때 평가기 프로세스가 60초 안에 준비 신호를 못 보낸 사건이 있었어. 자식이 학습 전체를 다시 시작하느라 바빴던 거야.

11.4 안전장치: 실패하면 옛 경로로

워커가 죽거나, GPU 오류가 나거나, IPC가 끊기거나, 멈추면(stall_timeout 동안 평가 flush도 끝난 판도 없으면) 풀을 내리고 그 에폭을 fallback()(옛 selfplay_mp.py 경로)으로 다시 돌려. 킬 스위치 파일 MP_UNIFIED_OFF를 만들면 통합 풀을 끌 수 있고, 검토 후 옛 스위치 MP_SELFPLAY_OFF도 같이 먹게 고쳤어.

12. 종료와 큐 비우기: 좀비 트레이너 문제

12.1 무엇이 위험했나

배포 전 검토(2026-09-26)에서 나온 "Major" 문제야. 한 에폭의 작업을 모두 큐에 미리 넣어두는데(작업 수 > 워커 수), 에러가 나서 아직 큐에 작업이 남은 채로 종료하면 어떻게 될까?

  1. multiprocessing.Queue는 내부에 "피더 스레드"가 있어서 넣은 항목을 파이프로 밀어 넣어.
  2. 읽는 쪽(워커)이 죽었으면 파이프가 가득 차서 피더 스레드가 쓰기에서 멈춰.
  3. Python은 종료할 때 이 피더 스레드를 join(끝날 때까지 기다림)해. → 영원히 기다림.
  4. 프로세스는 살아 있지만 아무 일도 안 함. 워치독(14절)은 "프로세스 살아 있음"만 보니까 재시작하지 않음. → 학습이 조용히 멈춤.

12.2 수정

# ... Never join these feeders; shutdown() also drains.
for q in (self.task_queue, self.result_queue, self.ready_queue, self.error_queue):
    q.cancel_join_thread()

그리고 shutdown()은 세 단계로 정리해.

def shutdown(self, join_budget=5.0):
    # 1. Drop any still-queued (unplayed) tasks so workers reach their
    #    sentinel right after their current game instead of playing on.
    empty_polls = 0
    while empty_polls < 2:
        try:
            self.task_queue.get(timeout=0.05)
            empty_polls = 0
        except pyqueue.Empty:
            empty_polls += 1
        ...
    for _ in self.workers:
        self.task_queue.put(None)        # 워커마다 종료 표시
    # 2. Stop the GPU coordinator and close our pipe ends: a worker
    #    blocked on (or about to make) an eval request fails fast with
    #    EOF/BrokenPipe, reports it, then reads its sentinel and exits.
    ...
    # 3. One shared join budget for all workers, then terminate the rest.
    deadline = time.monotonic() + join_budget
    ...
  • 1단계 큐 비우기: 아직 안 둔 작업을 꺼내 버려서, 워커가 지금 판만 끝내고 바로 종료 표시(None)를 만나게.
  • 2단계: 코디네이터를 멈추고 부모 쪽 파이프를 닫으면, 평가 요청 중이던 워커는 EOF/BrokenPipe로 즉시 실패하고 종료 표시를 읽고 나가.
  • 3단계: 모든 워커가 하나의 공유 시간 예산(5초) 안에 join. 워커 10개가 각각 5초씩 50초를 쓰지 않게. 남은 놈은 terminate().

시험 결과 "정상 종료 22초"가 확인됐고, 옛 selfplay_mp.py에도 같은 패치를 넣었어. 그밖에 시작 중 워커가 죽으면 3분 기다리지 않고 즉시 대체 경로로 가도록, 속도 통계가 시작 후 누적값이라 효과가 안 보이던 것을 에폭별 값으로 바꾸는 수정이 함께 들어갔어.

7.3절의 "같은 국면이면 트리 유지" 덕분에, 목표 방문 수를 16, 32, 48 … 로 올려가며 같은 트리를 키울 수 있어. 매 조각 뒤 스냅샷(후보별 방문, Q값, 신경망 원래 정책·가치, PV)을 저장하고, 브라우저는 폴링으로 이걸 받아 그려. 그래서 AI가 "생각하는 과정"이 실시간으로 보여. 조각 크기를 배치 크기와 같게 한 이유는, 조각이 배치보다 작으면 그룹이 덜 차서 GPU 효율이 떨어지기 때문이야. 인자를 보면 c_puct 1.414, 노이즈 끔(False), 강제 탐색 끔(0.0)이야.

gen(세대 번호)은 "생각하는 도중 새 게임을 눌렀을 때" 옛 스레드의 결과가 새 게임에 섞이지 않게 하는 장치야.

17.3 해석: 병목은 GIL이 아니라 GPU 계산

두 측정 모두 같은 그림을 그려. 사용자 수에 거의 비례해서 시간이 늘어나(4명 ≈ 4배, 8명 ≈ 7배, 6판 ≈ 5배). 만약 병목이 GIL이나 Python 오버헤드였다면, 묶기로 호출 수를 줄였을 때 큰 개선이 있었어야 해. 만약 병목이 "작은 배치라 GPU가 놀아서"였다면, 묶어서 배치를 키웠을 때도 큰 개선이 있었어야 해. 둘 다 아니었다는 건 GPU가 이미 실제 계산으로 꽉 차 있다는 뜻이야.

  • GTX 1050은 학습(역전파)과 자기대국 평가를 동시에 하고 있어. 웹 손님은 남는 GPU 시간만 얻어.
  • 엔진은 이미 16개씩 배치로 보내고 있었어. 배치 16이 이미 이 GPU에서 "충분히 큰" 크기였다면, 6게임을 합쳐 96개로 만들어도 처리량(초당 국면 수)은 거의 같고, 일의 총량이 같으니 시간도 같아.
  • 엔진이 탐색 중 GIL을 놓기 때문에(3절) 스레드끼리 CPU 쪽 탐색은 이미 겹쳐서 돌고 있었어.

당시 기록의 첫 추정은 "GPU 계산이 아닌 다른 곳(입력 변환 Python 코드, 탐색 코드)"이었는데, 이후 측정이 이를 "GPU 순전파"로 정정한 것으로 보여. 결론은 실용적이야. 동시 접속 한계는 1100회 기준 대략 5~8명이고, 늘리려면 탐색 수를 낮추거나(600회면 약 2배) 학습을 멈추거나 GPU를 바꿔야 해. 묶은 방식은 해가 없어서 다음 재시작 때 적용했어.

실제 사건(2026-09-28). 친구가 "멈췄다"고 했을 때, 서버는 0.03초, 터널은 0.2초로 정상 응답 중이었어. 3명이 동시에 두며 3판 모두 AI가 생각 중이라 한 수가 혼자일 때의 약 3배 걸렸던 거야. 어려움(1100회) 15~20초, 최강(2000회) 30초 이상. 그 전에 부하 시험 자체가 약 1분간 GPU를 같이 써서 느려졌을 가능성도 기록에 적혀 있어. 성능 측정도 운영 중인 시스템에 부하를 준다는 걸 잊으면 안 돼.
